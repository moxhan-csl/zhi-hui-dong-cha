## 0. 文档说明与阅读指引

### 0.1 这份文档写的是什么

这份文档描述**已经实现并上线的东西**，不是愿景。它的读者是：

- 接手维护的人：需要知道每个页面的字段规则、每个接口的真实响应、每张表的真实列。
- 做验收的人：需要知道每条 AC 的判定口径来自哪一行代码，以及当前为什么判不了。
- 做设计对齐的人：需要知道哪些能力**代码里根本没有**，别当成既有能力继续往上叠（§12）。

**本文档的唯一事实来源是代码。** 早前的两份文档（接口契约与设计需求提取文本）已经删除，正文不再引用它们，也不再与它们做差异比对——两份已经不存在的东西之间谁对谁错没有意义。文档分工只剩两条：

| 文档 | 内容 | 权威范围 |
|---|---|---|
| **本文档** | 功能 + 数据库 + 权限 + 配置 + 验收 + **能力边界** | 现状总览；一切结论以代码为准，逐条给出 `文件:行号` |
| `docs/缺陷与技术债.md` | 已知缺陷与技术债分级清单（D-1~D-51，高 15 / 中 21 / 低 15） | **缺陷的唯一登记表**（§13 只留指针；**这一串编号现在到 D-51**——2026-10-02"给后端补注释"那一轮逐方法读码核实后又登记了十条 D-42~D-51，那条注释 bug 本身没编号，核实过程与判为不成立的几条写在它的 §5.13）。编号 `D-n` 全站通用 |
| `docs/DEPLOY.md` | 部署与发版操作 | 唯一部署文档（runbook 式，标注在哪台机器执行、填错会怎样），本文 §9 只摘要并指向它 |

冲突时的优先级：**代码 > 本文档**。发现本文档与代码不一致，直接改本文档并在 §12/§13 登记。

标注约定：

| 标记 | 含义 |
|---|---|
| `[已实现]` | 代码里有，线上能跑 |
| `[边界]` | 这件事**没有被实现**，或实现的口径容易被想当然（原先常被当成"已有能力"的那些） |
| `[未实现]` | 代码里没有对应实现。**不要在设计里假设它存在** |
| `[缺陷 D-n]` | 实现本身有问题，全表见 §13 |
| `文件:行号` | 结论出处。行号随改动漂移，符号名不会 |

**隐私与凭据约定**：本文档**不记录任何主机地址、端口对应的真实实例、账号名与口令**。需要指代环境时写作 `<APP_HOST>`（应用对外地址）与"生产库主机"。口令与 JWT 密钥的真实值只在服务器的 `/opt/dongcha/.env`（不进镜像、不提交，仓库里没有副本）；**`docs/DEPLOY.md` 是仓库里唯一保留真实主机地址的文档**，因为它按 runbook 写、命令要能直接粘贴执行——这是 2026-09-30 明确定下的边界，**不要"顺手"把它也脱敏成占位符**。`application.yml` 曾带着生产实例的 host 与通用兜底口令/密钥（D-21、D-29），2026-10-01 第一批修复后统一改为 host `127.0.0.1` + 账号口令与 `JWT_SECRET` 留空，**仓库里现在没有任何出口地址与凭据形态的默认值**；本文 §8 的配置表只写变量名、默认值形态和填错的后果。

本文档**不写任何未经代码或接口实测证实的数字**；旧文档里那些示例数值已随文件删除一并作废，见 §0.3 第 3 条与 §12.2。

### 0.3 全站统一的三条口径（唯一权威，正文只引用不重述）

1. **未知量的表达**：分母为 0 或本进程测不到 → 后端返回 `null`，前端显示"—"；评测汇总里模型未判定 → 返回 `-1`，前端显示"未判定"。两者**都不得**折算成 0 或 100%。出处 `EvalService.java:204-214`、`MonitorService.percentile`（空样本返回 `null`，D-19 已修）。
2. **百分比刻度**：`metrics.*`、`vectorRate` 等百分比字段一律是 **0-100 数值**，前端不得再乘 100。唯一例外是引用的 `score`，它是 0-1 余弦相似度。
3. **数字必须有出处**：本文档里出现的每一个数值，要么给出 `文件:行号`，要么给出实测日期与接口。任何未由当前代码或当前实测支撑的历史数字（包括已删除文档里的示例值，如"检索准确率 92%""Golden Set 200 条"）**一律不作为事实引用**，见 §12.2。

## 1. 产品定位与核心流程

### 1.1 一句话定位 `[已实现]`

企业级 RAG 知识助手：员工自然语言提问 → 系统在 pgvector 里检索企业知识库分块 → 通义千问基于检索片段生成带 `[n]` 行内引用的回答 → SSE 流式下发到 Vue 前端。全程不涉及模型微调，领域适配靠 Advanced RAG（查询改写 + 多查询扩展 + 阈值过滤）与 Prompt 工程。

诚实性是一条产品级约束，不只是工程细节：**没有分母的指标返回 `null`（前端显示"—"），模型没判定的返回 `-1`（前端显示"未判定"），没有已复核考卷时拒绝出分**。任何情况下不得把未知折算成 0% 或 100%。出处 `EvalService.java:98-100,244-249`。

### 1.2 一问一答的实际链路

```
前端 ChatView
  └─ POST /api/chat/stream  (JWT, SSE)
      ├─ AuthWebFilter：验令牌 + 角色矩阵           security/AuthWebFilter.java:44-72
      ├─ ChatService：scopeOf → Visibility.scopeFor(可见库 ∩ 请求指定库)   rag/Visibility.java
      ├─ ChatGuard.acquire：日成本熔断 → 单用户日次数 → 在途并发   chat/ChatGuard.java
      ├─ 命中回答缓存（代号+问题+范围+历史窗口）？→ 直接回放 + skipped 状态   chat/ChatService.java
      └─ 未命中：
           1 intent      正则识别，不调模型            [边界] 常被误当作"意图识别智能体"
           2 retrieval   查询改写/多查询 → embed → pgvector 近邻 → 阈值+topK
           3 synthesis   最多 4 片段进 prompt → LLM 流式生成 → 规整 [n] 标号
           4 validation  LLM-as-Judge 忠实度打分，≥60 通过
                         未通过 → 带改进指令回 3 重写（最多 1 次，检索不动）   [缺陷 D-1 已修]
      └─ 事件：start → agent-update* → token* → citation → revision? → done/error
      └─ 落库：conversations / messages / citations（MySQL），chat:<sha1>（Redis，TTL 600s，代号 chat:gen）
```

### 1.3 术语表（正文用词以本表为准）

| 术语 | 在本项目里的确切所指 |
|---|---|
| 多智能体管道 | **固定四段管线的可视化状态**（intent/retrieval/synthesis/validation），不是 LangChain4j 的 agent 编排。四段都在同一线程顺序执行，`intent` 是正则。`[边界]` 不是智能体编排 |
| 知识库（KB） | MySQL `knowledge_bases` 的一行 + 其下文档分块的 `kb_id` 集合。可见性由 `scope` + `members` + `owner` 决定。正文一律写"知识库"，**不与"数据库"混称"库"**；指 MySQL/PG 时写全名 |
| 分块 | pgvector `chunks` 表的一行，500 字符窗口 / 100 重叠，含 1024 维向量。正文统一写"分块"，数量写"分块数"。`TextChunker.java:12-13` |
| 引用（citation） | 后端检索阶段生成、随回答下发的**来源卡片**（最多 4 张），对应 `citations` 表一行 |
| 标号（marker） | 回答正文里的行内 `[n]`。**标数是模型产出的，引用卡片数是系统给出的**，两者可以不等——引用完整率度量的正是这个差 |
| 题库 | MySQL 表 `golden_questions`。**题目** = 表的一行；**题集** = 一次评测所选的题目集合（用 `question_signature` 标识）。代码文案里的"考卷"即"题目"，保留原文时注明 |
| 题集指纹 | `sha1(排序后的题目 id 列表)` 前 8 字节 hex + `:` + 题数，形如 `a1b2c3d4:30`。**只有指纹相同的两次评测可比**，换了题集就是另一条测量线 |
| 已复核 | `golden_questions.status='reviewed'` 且有 `reviewed_by`。是题目进入评测的唯一准入条件之一 |
| 降级 / 退化 | 同一件事，正文统一写"**降级**"：外部依赖不可达时改用内存实现。字段取值对应关系：`llm: openai-compatible ↔ mock`、`vectorStore: pgvector ↔ memory`、`redis: redis ↔ in-memory`、`status: UP ↔ DEGRADED` |
| 访问令牌 / 刷新令牌 | JWT 的两个 token。**与"token 事件""LLM token 计数"无关**——后者一律写"LLM token"或"字数/token 用量" |

要点（`docker-compose.yml:1-89`、`frontend/nginx.conf`）：

- **只有两个应用容器**。MySQL/Redis/PG 用宿主机现成实例，经 `host.docker.internal:host-gateway` 访问；容器里写 `127.0.0.1` 必然连不上。
- 后端 8080 **只绑 `127.0.0.1`**，外部流量一律走前端 `/api` 反代。
- nginx 的 `proxy_pass` 用变量 + `resolver 127.0.0.11`，避免后端容器没起来时 nginx 启动即退出。
- 服务器**不做任何编译**：jar 与 dist 由开发机产出，镜像只 `COPY`（`Dockerfile.prebuilt`）。

### 2.5 降级矩阵（谁能退化、谁不能）

| 依赖 | 不可达时 | 影响 | 恢复 | 出处 |
|---|---|---|---|---|
| MySQL | **不退化，读路径每请求真查、挂了就直接报错** | 业务数据是底座，缺了没有意义 | 修好连接重试 | `SeedInitializer`（启动只灌 users 镜像与运行期配置，载入失败则跳过三项对账并 ERROR 日志）、DEPLOY.md |
| LLM（含 embedding） | `FallbackLlmProvider` → `MockLlmProvider`，`/api/health llm=mock`，`status=DEGRADED`。**流式降级有两种形态，第二种以前没写清**：订阅前就知道真服务不可用 → 整条走 mock（干净）；真流**半路断** → `onErrorResume`（`FallbackLlmProvider.java:43-47`）把 mock 文本接进**同一条回答**，用户在连贯的一个气泡里读到缝合内容，而 `done.provider:"mock"`、`done.llmAvailable:false` 都要等整条流跑完才下发（登记为 **D-45**，只读码核实、本机无真模型凭据、未观测） | 回答是模板文本；**向量化默认拒绝**（D-14 已修）：入库停在 `FAILED`、检索抛 `RetrievalFailedException`，不再静默写 1024 维哈希假向量（它与真向量同维、事后无法区分）。只有显式 `LLM_ALLOW_HASH_VECTORS=true` 才允许写，并每次一条 WARN | 每 30s 重探（`LLM_PROBE`/启动探测）；严格调用成功即自愈 | `application.yml:55-57`、`FallbackLlmProvider.embedStrict`、`HashEmbedder` |
| pgvector | `DelegatingChunkStore.degrade()` → `MemoryChunkStore`，队列化写（上限 2000），全站问答可能零命中 | 降级**不是粘性的**：`PgStoreRecovery` 每 `PG_REPROBE_MS` 重探，探通自动切回并回放排队写（早期文档与脚本注释写"只有重启才恢复"是错的，第三批已随 D-22/D-12 一并改掉） | `PG_REPROBE_MS=30000` | `DelegatingChunkStore.java:25,226`、`PgStoreRecovery` |
| Redis | `redis: in-memory`（内存 map 兜底） | 登录冷却与成本统计丢失（不阻断） | — | `/api/health` 字段 |

> 关键运维事实：**降级不阻碍启动，很容易看漏**。上线后必须回查 `/api/health` 的 `status/llm/vectorStore/redis`，而不是只看容器 Up。
>
> **pgvector 降级的恢复是自动的**（本节的权威结论）：`PgStoreRecovery` 每 `PG_REPROBE_MS=30000` 探一次，探通即切回 `pgvector` 并回放降级窗口内排队的写（队列上限 2000，超出会丢弃并记 ERROR）。`scripts/acceptance/run.mjs` 的前置注释原先写着"只有重启才会恢复"，2026-10-01 第三批已按本节改写（降级会自动愈合，但**降级窗口内的问答结论仍不可信**，所以 preflight 检查本身保留）。但要注意：LLM 的 `availability.llm` 只有在一次严格调用成功后才自愈，所以 `/api/health llm=mock` 在重启前可能一直显示 mock。**"自动愈合"有两处已登记的边界，别把它读成无损**：回放失败时未完成的写会整段退回**队尾**，于是与降级期间新到的同文档写操作顺序颠倒，而覆盖式写入（先 `DELETE` 再 `INSERT`、无事务）让旧内容盖住新内容且没有任何日志会说这件事（**D-43**）；探针 `probePg` 调的是整套 `initSchema`，维度不符即 `TRUNCATE TABLE chunks`（**D-42**）。两条都只有静态读码证据，本机无 PG、未复现，见 `缺陷与技术债.md` §5.13。

## 3. 角色与权限

### 3.1 角色定义 `[已实现]`

三个枚举值，存 `users.role`（`VARCHAR(20)`）：

| 角色 | 代码里的常量值 | 实际能力 |
|---|---|---|
| `EMPLOYEE` | 普通员工 | 问答（受可见库限制）；`GET /api/knowledge-bases`、`GET /api/documents`（读放行，但前端路由不给他入口） |
| `KM_ADMIN` | 知识管理员 | + 知识库/文档写操作 + 评测中心全部 + 题库 |
| `SYS_ADMIN` | 系统管理员 | + 监控中心 + 系统设置（模型/RAG/用户/审计）+ 全部库可见 |

### 3.2 后端鉴权矩阵（`AuthWebFilter.checkRoleMatrix`，唯一权威）

先过身份，再过矩阵。身份三档 401 文案不同（便于排障，不泄露账号存在性以外的信息）：

| 情形 | 状态码 | code | message |
|---|---|---|---|
| 无 `Authorization` 或非 `Bearer ` | 401 | `UNAUTHORIZED` | 未登录或 Token 缺失 |
| 验签/过期失败 | 401 | `UNAUTHORIZED` | 登录已过期，请重新登录 |
| `sub` 查不到用户或 `enabled=false` | 401 | `UNAUTHORIZED` | 账号不存在或已停用 |
| 角色不足 | 403 | `FORBIDDEN` | 见下表 |

矩阵（`path.startsWith` 前缀匹配 + 方法是否可变 POST/PUT/DELETE/PATCH）：

| 路径前缀 | 要求 | 403 文案 |
|---|---|---|
| `/api/monitor` | `SYS_ADMIN`，**任意方法** | 仅系统管理员可访问监控中心 |
| `/api/settings` | `SYS_ADMIN`，**任意方法** | 仅系统管理员可访问系统设置 |
| `/api/eval` | `KM_ADMIN+`，**任意方法** | 需要知识管理员及以上角色 |
| `/api/knowledge-bases` | 仅**可变方法**需 `KM_ADMIN+`；GET 全登录用户放行 | 知识库写操作需要知识管理员及以上角色 |
| `/api/documents` | 仅**可变方法**需 `KM_ADMIN+`；GET 全登录用户放行 | 文档上传/重试/删除需要知识管理员及以上角色 |
| `/api/chat/**` | 全登录用户 | — |
| `/api/auth/login`、`/api/auth/refresh`、`/api/health` | 公开（`PUBLIC_PATHS`） | — |
| 非 `/api` 前缀、CORS 预检 `OPTIONS` | 直接放行 | — |

> `[边界]` 两处最容易被想当然的权限：① `/api/settings` 下**所有**端点都要 SYS_ADMIN（`AuthWebFilter.java:82`），包括用户列表的读取，KM_ADMIN 调进去就是 403；② `/api/monitor` **仅 SYS_ADMIN**（`:81`），知识管理员看不到监控中心。两处的判据都是 `path.startsWith`，不看方法也不看资源归属。
>
> **关于"GET 对 EMPLOYEE 放行"是否构成越权**：不构成。读接口**在业务层按可见知识库过滤**——`DocumentController.list` 跳过 `kbId` 不可见的文档（`DocumentController.java:57-63`），`/documents/{id}` 与 `/documents/{id}/chunks` 都走 `requireVisible`，不可见即 403「无权访问该文档」（`:219-226`）；会话同理，非本人会话 403「无权访问该会话」（`ChatService.java:364/:413/:430`）。
> `[缺陷 D-6 已修，第五批]` 曾经的**口径不一致**（前端路由把 `/documents`、`/knowledge` 标 `minRole: 'KM_ADMIN'`，后端却允许 EMPLOYEE 调这两个 GET）已按后端为准统一：两条路由去掉 `minRole`、侧栏降到 `EMPLOYEE`、写操作在视图内按角色隐藏（详见 §3.3）。**核实结论是"后端矩阵是对的"**，所以收紧的是前端展示层，`AuthWebFilter` 一行没动。留下的如实边界：员工现在能在知识库页看到聚合统计（含全局"当日模型 Tokens"），这是对齐矩阵后**有意接受**的结果，不是漏项。

### 3.3 前端路由守卫（体验层，不替代服务端）

`frontend/src/router/index.ts`：meta `minRole` + `store.atLeast()`，不足则跳 `/chat`；未登录跳 `/login?redirect=`。路由表见 §7.3（8 个页面 + 1 个父布局 + 2 个 redirect = 11 条记录）。

**与 §3.2 矩阵的对应关系（D-6 已对齐）**：`/knowledge` 与 `/documents` 两条路由**不再有 `minRole`**，`SideNav.vue` 里对应两项也降到 `EMPLOYEE`——因为后端矩阵对这两个模块只收紧写操作（POST/PUT/DELETE 需 KM_ADMIN+），GET 对所有登录用户放行且内容按可见库过滤。"能看不能改"由视图内部的 `canWrite = atLeast('KM_ADMIN')` 承担：文档页隐藏上传/批量删除/多选列/操作列，知识库页隐藏"编辑/删除"与新建按钮。**这条不是前端客气**：`/api/settings/models` 只有 SYS_ADMIN 可读，知识库页原本无条件请求它，KM_ADMIN 点"新建"必吃一个"权限不足"弹窗，现在按角色决定要不要发这个请求（拿不到就显示占位文案）。

### 3.4 知识库可见性（`Visibility.canSee`，五步短路）

```java
if ("SYS_ADMIN".equals(user.role)) return true;                    // 1
if ("KM_ADMIN".equals(user.role) && !"confidential".equals(kb.scope)) return true; // 2
if ("public".equals(kb.scope)) return true;                        // 3
if (kb.owner != null && kb.owner.equals(user.id)) return true;     // 4
return sharedWith(user, kb);                                       // 5
```

`sharedWith` 匹配 `kb_members.member`，命中任一即可见（`Visibility.java:46-51`）：

- `user.id`
- `user.empNo`
- `user.account`
- `"dept:" + user.dept`

检索时同样生效：求交逻辑只有一处实现 `Visibility.scopeFor(user, requested)`（D-34 已合一），`ChatService.scopeOf` 与 `RetrievalService.retrieveForChat` 都调它——第六批删掉容错检索入口 `retrieve()` 之后，**问答与评测共用这唯一一条检索路径**，不存在第二个口径。不可见或不存在的 id 被剔除（不报错），交集为空则退化为"在全部可见库里搜"；剔除数量与实际范围写进检索阶段的 `agent-update` detail，用户能在页面上看到"你以为的限定没有生效"（D-9）。

成员那四个字段的**写入侧校验**在 `KnowledgeBaseController.validateMembers`（D-7）：非 `dept:` 形态必须能在用户表里对上 user id / 工号 / 账号（后两者大小写不敏感），对不上直接 400 并指名是哪一项；`dept:部门` 允许暂时没人（只打 WARN）。校验读的是 `db.allUsers()`（直查 MySQL）而不是 60s TTL 的内存镜像，免得"刚建完账号就分享"被误拒。以前这些错写是**静默不可见**——库建了、成员填了、人看不见。

### 3.5 机密库的二次确认

`POST /api/knowledge-bases` 且 `scope=confidential` 时，必须带 query `?confirm=true`，否则 428 `CONFIRM_REQUIRED`（`KnowledgeBaseController.java:95-98`，HTTP 状态用 `PRECONDITION_REQUIRED`）。`[边界]` 这道闸门**只在创建时**生效；`PUT` 改成 confidential 未走该闸门，也没有"机密库不允许转换成其他范围"的限制。

## 4. 数据库设计

### 4.1 存储分工

| 存储 | 放什么 | 不放什么 |
|---|---|---|
| **MySQL `zhihu_dongcha`** | **13 张 JPA 映射表**（11 张实体表 + `kb_members`/`conversation_kb_ids` 两张 `@ElementCollection` 集合表）：用户、知识库、文档元数据、会话/消息/引用、评测运行、题库、设置、审计。另有一张代码已不映射的物理死表 `eval_samples`（§4.4.8）。原写法"12 张"是数错了，第九批 D-2 用 `DdlGen` 离线生成 DDL 时按 `create table` 计数订正 | 向量 |
| **PostgreSQL `kbqa` + pgvector** | 1 张 `chunks` 表：分块正文 + 1024 维向量 | 文档状态、用户 |
| **Redis** | 登录冷却、语义回答缓存、token/成本计数 | 任何唯一真相源（丢了可重建） |
| **磁盘 `app-uploads`** | 上传原始文件（命名卷） | 解析中间产物 |

> `documents` 表与 `app-uploads` 卷**必须成对备份恢复**：只恢复表会让 retry 找不到文件，只恢复卷则列表里没有它们。见 `DEPLOY.md` 第 12 节。

### 4.2 建表机制与后果

- `ddl-auto: update`（`application.yml:22`）：启动时按实体 diff 建表/加列。
- **没有迁移工具、没有版本化 DDL**（仓库里的 `.sql` 全是运维核对脚本，不是迁移）。
- 后果：① 列只加不改不删，改名等于丢数据。加**可空**列是安全的（第八批给 `documents` 补 `stage` 就走这条路：旧 jar 读新库不受影响，新 jar 读旧库该列为 NULL）；② **索引可以写在实体上**（第九批 D-2 起七个实体用 `@Table(indexes=…)` 声明了 12 条，见 §4.7），但 `ddl-auto: update` 是按**索引名**判存在、并按名字建，它不会告诉你生产库上到底建成了什么——核对办法是 `SHOW INDEX` / `information_schema.statistics`，或离线跑 `backend/tools/DdlGen.java` 看生成的语句文本；③ **UNIQUE 约束刻意一个都不加**（共享生产实例，存量脏数据会让写入直接失败），业务唯一性由写入侧代码拒绝；④ MySQL 侧给该库 `ALL PRIVILEGES` 即可，PG 侧要额外授权（`DEPLOY.md` 13.3）。
- 实体字段普遍**没有写 `nullable = false`**（全项目 grep 零命中），但**这不等于列可空**：`boolean / int / long / double` 等原始类型列由 Hibernate 生成 **NOT NULL**（`users.enabled`、`documents.progress/chunk_count/created_at/updated_at`、`messages.ord`、`citations.idx/page/score`、`golden_questions.enabled` 都在此列）。真正可为 NULL 的是对象类型列：`String`、`Long`、`Double` 与所有 `@Lob`。
- `@Lob` 长文本映射成 `TEXT` / `LONGTEXT`（列定义在实体里显式写了 `columnDefinition`）。
- Jackson `default-property-inclusion: non_null`（`application.yml:8`）：**后端返回 null 的字段直接从 JSON 消失**，前端拿到 `undefined` 才能显示"—"。写前端时不能假设字段一定存在。

### 4.3 ER 关系（实况）

```
users (id) ──1:N──> conversations (user_id)          ── 冗余列，无 FK
                    conversations ──@OneToMany(cascade=ALL, orphanRemoval)──> messages (conversation_id)
                    messages ──@OneToMany(cascade=ALL, orphanRemoval)──> citations (message_id)
                    conversation_kb_ids (元素表，conversation_id → kb_id 字符串)
knowledge_bases (id) ──元素表 kb_members (kb_id → member)──┐ 成员仍是自由字符串列，但**写入时逐项校验**（D-7）
knowledge_bases ──> documents (kb_id 冗余列，无 FK)
documents     ──> chunks.doc_id (PG，无跨库 FK)
golden_questions  ──(运行时取题，无 FK)──> eval_runs (question_ids TEXT 快照 + question_signature + env_json)
eval_runs ──> eval_samples (run_id 冗余列)  ← **代码侧实体已删（D-3）**，物理表仍在等 DROP，见 §4.4.8
settings_models / settings_rag  (k/v 纵表)
audit_logs  (actor 是 account 字符串，无 FK)
```

两个真实的 ORM 关系只有 `conversations→messages→citations`（级联删除靠它）。其余全是**冗余 String 列 + 应用层拼装**，跨表一致性完全由代码保证。

### 4.4 MySQL 表逐张字段清单

所有表的 `id` 均为**应用侧生成的 UUID 字符串**（`UUID.randomUUID().toString()`，`VARCHAR(40)`），只有 `citations` 与 `eval_samples` 用自增 `auto_id`。时间戳统一为 `BIGINT` 毫秒（实体里 `Long`），无数据库默认值。

#### 4.4.1 `users`

| 列 | 类型 | 约束 | 语义 |
|---|---|---|---|
| `id` | VARCHAR(40) | PK | UUID |
| `name` | VARCHAR(60) | — | 显示名 |
| `account` | VARCHAR(120) | **unique=true**（全项目唯一的列级唯一） | 邮箱或工号，登录名 |
| `emp_no` | VARCHAR(60) | — | 工号，参与 `dept:` 之外的成员匹配 |
| `password` | VARCHAR(120) | — | BCrypt 串 |
| `role` | VARCHAR(20) | — | `EMPLOYEE`/`KM_ADMIN`/`SYS_ADMIN` |
| `dept` | VARCHAR(60) | — | 部门，参与 `dept:<部门>` 成员匹配 |
| `enabled` | BOOLEAN | — | 停用后 401「账号不存在或已停用」 |

`account` 的 `unique=true` 是**全项目唯一的一条历史遗留列级 UNIQUE**，第九批 D-2 没有新增任何约束。"账号/工号不撞车"由 `SettingsController.requireDistinctIdentity` 在写入时检查（建号查 `account` 与 `empNo` 两个方向，改号只在工号真的变化时查）；它比的是忽略大小写的**交叉**关系——`account` 撞别人的 `emp_no` 也算撞车（原先只查同名列，这一方向能过，结果是那个工号永远解析到账号持有者、另一个人无声地登不进来）。**`users` 有意不建新索引**：登录走 `findByAccountIgnoreCase`/`findByEmpNoIgnoreCase`，Spring Data 生成的是 `lower(列)=lower(?)`，函数包住列之后二级索引就用不上，而 `users` 是全站最小的表。详见 §4.7。

#### 4.4.2 `knowledge_bases`

| 列 | 类型 | 语义 |
|---|---|---|
| `id` | VARCHAR(40) PK | UUID |
| `name` | VARCHAR(120) | 界面显示名 |
| `scope` | VARCHAR(20) | `public`/`internal`/`dept`/`confidential` |
| `owner` | VARCHAR(40) | 创建者 user id（可见性第 4 步） |
| `owner_name` | VARCHAR(60) | 冗余显示名 |
| `created_at` | BIGINT | 列表按它升序排（第八批起是 SQL `order by`）。**这一列有意不建索引**（第九批 D-2 的判定：行数由管理员控制、唯一读路是 `findAll` 全量取，全量扫小表时优化器本来就不会用二级索引，加索引只多付一次写成本），见 §4.7 |

库名**在写入时判重**（第九批 D-2）：建库与改名两处按 `Names.key`（trim + 忽略大小写）比对**其它**库的名字，撞上就 400 `KB_NAME_DUPLICATE`；改自己成原名不挡自己。**这不是 UNIQUE 约束**，读后写不原子（并发建同名仍可能双双通过），详见 §4.7 与 §5.3。

配套元素表 **`kb_members`**：`kb_id` VARCHAR(40) + `member` VARCHAR(80)。`member` 是**自由字符串**，四种形态：user id / empNo / account / `dept:部门名`。没有格式校验，写错就是静默不可见。`[缺陷 D-7]`（第五批已改为写入时逐项硬校验）。`kb_id` 是集合表外键列，**D-2 有意不为它声明索引**：生成的 DDL 里带 FK 约束，InnoDB 建外键时会自动为外键列建索引，再按名字声明一份只是多出一个同列重复索引。

#### 4.4.3 `documents`

| 列 | 类型 | 语义 |
|---|---|---|
| `id` | VARCHAR(40) PK | UUID；上传不返回固定 id |
| `name` | VARCHAR(255) | 原始文件名 |
| `type` | VARCHAR(20) | 扩展名 `pdf`/`docx`/`xlsx`/`txt`/`md` |
| `kb_id` | VARCHAR(40) | 所属库（冗余，无 FK） |

| `status` | VARCHAR(20) | `PENDING`/`PARSING`/`READY`/`FAILED` |
| `progress` | INT | 0/25/50/…/100，失败重置 0 |
| `chunk_count` | INT | 解析完成后回填的声明块数 |
| `fail_reason` | VARCHAR(500) | 根因（应用层截 200 字） |

**索引（第九批 D-2）**：`idx_documents_kb_id (kb_id)`、`idx_documents_status (status)`、`idx_documents_updated_at (updated_at)`——分别服务 `findByKbId`/`existsByKbId`、`findByStatusIn`（启动对账）、`findAllByOrderByUpdatedAtDesc`（`GET /api/documents` 每请求直读）。
**同一库内不允许同名文档**：上传时在**落盘之前**按 `Names.key` 比对同库现有文件名，撞上就 400 `DOC_NAME_DUPLICATE`（顺序有讲究：判重排在 `transferTo` 之后会在 `uploads` 卷里留一份没人认领的文件）。要替换只能先删旧文档（删除会一并清向量与落盘文件）。同样**不是 UNIQUE**，读后写不原子。

**`stage` 在第八批之前不落库**（它原先只是内存镜像对象上的运行期字段），镜像删除后它必须落列，否则前端轮询到的进度只剩百分比、看不出卡在哪个阶段。落列由 `ddl-auto: update` 在发版后第一次启动时补齐，**已入库的行该列为 NULL**，前端按状态兜底显示"处理中"（`DocumentsView.vue:55`），重新解析后才有值——这是缺读数，不是脏数据。也没有 `owner` 列：文档归属只由库决定。

#### 4.4.9 `golden_questions`（题库，取代 jar 内的 `golden_set.jsonl`）

| 列 | 类型 | 语义 |

| `id` | VARCHAR(40) PK | — |
| `question` | TEXT | 题干 |
| `golden` | TEXT | 期望答案 |
| `expected_doc` | VARCHAR(255) | 期望来源文档；**为空则不允许复核** |
| `source` | VARCHAR(20) | `manual` / `imported` |
| `status` | VARCHAR(16) | `draft` / `reviewed` |
| `enabled` | BOOLEAN | 停用题不参与评测 |
| `note` | TEXT | 备注 |
| `created_by` / `reviewed_by` | VARCHAR(120) | account |
| `created_at` / `updated_at` / `reviewed_at` | BIGINT | — |

门禁三条（业务规则，不是列约束）：新建/导入**一律 draft**；题面/期望答案/期望文档任一变更即退回 draft 并清空复核人；`usable = status='reviewed' && enabled` 才进评测。
**题干判重（第九批 D-2）**：手工建题与改题干两处按 `normalize`（trim + 折叠连续空白 + 忽略大小写）比对全库题干，撞上就 400；导入本来就走同一口径的去重，现在两条路径不再能互相绕过。为什么必须拒：评测是**按题平均**的，同一道题存两次就占两份权重，而题集指纹只统计 id 集合，看不出"这两条其实是同一个问题"——分数失真且不留痕迹。同样**不是 UNIQUE**，读后写不原子。
**索引（第九批 D-2）**：`idx_golden_questions_updated (updated_at)`、`idx_golden_questions_created (created_at)`、`idx_golden_questions_status_updated (status, updated_at)`（"只列已复核题"筛完再倒序）。题干是 `TEXT` 列，判重**不建索引**、也不建前缀索引：它是每次写入时的一次全库列投影（只取 `question` 一列，`questionsOtherThan`），题量由人工录入控制。

### 4.5 PostgreSQL `chunks` 表 DDL（实况）

由 `PgChunkStore.initSchema()` 启动时逐条执行（`PgChunkStore.java:30-62`，以下为原文语义，`dim` 取 `LLM_EMBED_DIM`）：

```sql
CREATE EXTENSION IF NOT EXISTS vector;      -- 必须超级用户才能建，见 DEPLOY.md §6
CREATE EXTENSION IF NOT EXISTS pg_trgm;     -- 建了但没有任何查询用到
CREATE TABLE IF NOT EXISTS chunks (
    id          bigserial PRIMARY KEY,
    doc_id      varchar(64)  NOT NULL,
    kb_id       varchar(64)  NOT NULL,
    doc_name    varchar(255),
    chunk_index int          NOT NULL,
    page        int          NOT NULL DEFAULT 1,
    char_count  int          NOT NULL DEFAULT 0,
    content     text         NOT NULL,
    embedding   vector(1024)
);
CREATE INDEX IF NOT EXISTS chunks_doc_idx ON chunks (doc_id);
CREATE INDEX IF NOT EXISTS chunks_kb_idx  ON chunks (kb_id);
CREATE INDEX IF NOT EXISTS chunks_embedding_hnsw
    ON chunks USING hnsw (embedding vector_cosine_ops);   -- 失败则 WARN 并退化为顺序扫描
```

检索 SQL（`PgChunkStore.java:125-140`，参数全部走占位符绑定）：

```sql
SELECT id, doc_id, kb_id, doc_name, chunk_index, page, char_count, content,
       1 - (embedding <=> ?::vector) AS score
FROM chunks WHERE kb_id IN (?, ?, ...) AND embedding IS NOT NULL
ORDER BY embedding <=> ?::vector LIMIT ?
```

即 **`score = 1 - 余弦距离`**，每个查询向量各跑一次（多查询扩展在这里展开），按 chunk id 取最高分去重后返回 `topK`。`kbIds` 为空直接返回空集（不做全库检索）。**pg 降级时的内存实现与它不完全等价**：`MemoryChunkStore.java:92-97` 用 `double max = 0` 做起始值，负的相似度被 0 取代，而 pg 侧 `1 - 余弦距离` 可以是负数——两边只在**阈值设成 0** 时给出真正不同的命中集（0 是合法值，`SettingsController.java:117`；默认 0.15 时行为一致），此时内存实现会把可见库里的全部分块（截到 topK）当命中送进模型，而引用卡片显示的 `score` 一律 0.0，看不出"零相似"和"本该被排除"的区别。登记为 **D-48**。

**维度守卫**：启动时统计 `vector_dims(embedding) <> dim` 的行数，非零即 `TRUNCATE TABLE chunks RESTART IDENTITY` 并 WARN。也就是说**换 embedding 模型（维度变了）会自动清空整张向量表**——这是刻意的（旧向量与新模型不可混用），但它是不可逆动作，改 `LLM_EMBED_DIM` 前必须先备份 `chunks`。**触发点不止启动这一处**：这段守卫在 `initSchema` 里，而降级自愈的连通性探针 `DelegatingChunkStore.probePg()` 调的就是整套 `initSchema`（`PgChunkStore.java:55-61`、`DelegatingChunkStore.java:209-212`），所以"探测连不连得上"这个动作本身也能清表；加上建表用 `CREATE TABLE IF NOT EXISTS chunks`，同一 PG 实例里**别人的同名 `chunks` 表**若维度不同也在覆盖范围内。该形态登记为 **D-42**（只有静态读码证据，本机无 PG、未复现；核实过程见 `缺陷与技术债.md` §5.13）。

`page` 的 `DEFAULT 1` **实际从不生效**：插入路径总是显式带上 `c.page`（`PgChunkStore.java:71`），所以库里 `page=0` 的行是"无页边界"的如实记录（D-4 修复后仍会是 0——非分页格式与逐页失败的 PDF；PDF 逐页成功则写真实页号 1 起）。读回用 `rs.getInt("page")`（`:169`），字段语义见 §4.4.6。

**孤儿向量对账**（2026-09-29 加，下次发版进生产容器）：`SeedInitializer.reconcileOrphanVectors` 遍历 `chunks` 里 `distinctDocs()` 的 doc_id，凡 MySQL 已无此文档即 `deleteByDoc` 并打 WARN。**基准清单第八批起是 `SELECT id FROM documents`（原先是内存镜像的 keySet），读不到就整体跳过**——这条循环会删向量，半截基准等于把整库删光，所以 MySQL 未载入时同样整体跳过。此前删演示数据留了 5 个尾巴，现由该逻辑清掉。运维上**不要手工删 `chunks`**，交给对账。

### 4.7 索引与唯一性现状（务必知道）

> **本节写的是代码里的实体声明**（第九批 D-2，2026-10-01，**尚未发版**）。`ddl-auto: update` 会在新 jar 首次启动时把这些索引对**共享生产库**执行；发版之前，线上库里除了主键和那条遗留 UNIQUE 之外什么都没有。核对生产库实际有什么只用 `SHOW INDEX` / `information_schema.statistics`，**不要用本节反推库里状态**，也不要凭注解里有没有写来判断。

| 表 | 索引（除主键外） |
|---|---|
| PG `chunks` | `chunks_doc_idx`、`chunks_kb_idx`、HNSW `vector_cosine_ops`（`PgChunkStore.initSchema()` 启动时逐条 `CREATE INDEX IF NOT EXISTS`） |

|---|---|---|
| `documents` | `idx_documents_kb_id` / `idx_documents_status` / `idx_documents_updated_at` | `findByKbId`、`existsByKbId`/`hasDocsInKb`、`namesInKb`（同名判重）/ `findByStatusIn`（启动对账）/ `findAllByOrderByUpdatedAtDesc`（文档列表每请求直读） |

**三处有意不加，别"顺手补上"**：

- `knowledge_bases.created_at`——行数由管理员控制（几十量级），唯一读路是 `findAll` 全量取；全量扫小表时优化器本来就不会用二级索引，加了只多付一次写成本。
- `users` 的任何新索引——登录查询是 `findByAccountIgnoreCase` / `findByEmpNoIgnoreCase`，Spring Data 生成 `lower(列)=lower(?)`，**函数包住列之后索引就用不上**；`users` 又是全站最小的表。
- `kb_members.kb_id` 与 `conversation_kb_ids.conversation_id`——集合表的外键列，生成的 DDL 里带 FK 约束，InnoDB 建外键时自动为外键列建索引；再按名字声明一份只会多出一个同列重复索引。

**唯一性：数据库侧一条 UNIQUE 都不新增**（共享生产实例上存量行可能已经重名/撞号，约束一上去写入即失败，启动期 schema 迁移连带受影响；而"重名"是业务语义不是数据完整性）。全项目唯一的一条列级 UNIQUE 是历史遗留的 `users.account unique=true`。业务唯一性改为**写入侧代码拒绝**，四条口径：

| 对象 | 判重口径 | 拒绝点与返回 |
|---|---|---|
| 知识库名 | `Names.key`：trim + 忽略大小写 | 建库、改名两处 → 400 `KB_NAME_DUPLICATE`（改自己成原名不挡自己；改名判重排在 428 机密二次确认**之后**） |
| 同一库内的文档名 | 同上 | 上传时、**落盘之前** → 400 `DOC_NAME_DUPLICATE`（判重排在 `transferTo` 之后会在 `uploads` 卷留一份没人认领的文件） |
| 账号 / 工号 | 忽略大小写，**交叉比对**（`account` 撞别人的 `emp_no` 也算撞车） | 建号一次查两个方向（新账号、新工号各与其它所有人的两列比）、改号只在工号真的变化时查 → 400 `INVALID_PARAM`，文案点名冲突的那个人 |
| 题干 | `normalize`：trim + 折叠连续空白 + 忽略大小写 | 手工建题、改题干、导入去重三处同一口径 → 400 `INVALID_PARAM` |

四条共同的边界：**读后写、不原子**——同时建同名库、同时上传同名文件仍可能双双通过。这是"不加约束"换来的代价，不是可以修掉的 bug；真出现重名时删掉多余一条即可纠正。另外**存量脏数据不会被自动发现**（本批只拦"以后"，不追"以前"），核对办法是 `DEPLOY.md` 10.1 ⑤ 那四段只读 SQL。

**怎么核对生成的 DDL 长什么样（不连任何库）**：`backend/tools/DdlGen.java` 用 JPA 的 schema-generation 脚本设置离线打印建表语句；它与 `scripts/add-hot-read-indexes.mysql.sql`（同样 12 条 `CREATE INDEX`，供发版前主动执行）**同名同表同列序**，已逐条 diff 过。Hibernate 按索引名判存在，所以先跑脚本不会重复建。执行命令见 `DEPLOY.md` §10.1。

**为什么第八批之后这件事不再是"以后会变慢"**：五张业务表镜像删除后，`order by updated_at desc`（文档列表）、`order by at_time desc limit n`（审计）、`where kb_id=?`（删库前判空）、`where status in (?)`（启动对账）都成了 MySQL 侧的执行计划；镜像还在内存里时这些排序发生在 Java 侧，加索引的收益并不明显。表接近空时补索引是成本最低的一次。
**仍未实测的是收益不是语句**：线上 `documents=0`，加完索引快了多少无从测起——本批把"语句长什么样"从推断变成了证据，没把"效果"变成证据（`缺陷与技术债.md` §0 约定 2）。

引用完整性仍靠代码：`messages.ord`、`documents.kb_id` 之类不做级联（唯一真实的 ORM 关系是 `conversations→messages→citations`，见 §4.3）。

### 4.9 字段级语义坑（写代码/写前端前读一遍）

1. `null` 与 `-1` 的语义、百分比刻度见 **§0.3**，全站唯一口径，本节不重述。数据层面的直接后果是 Jackson `default-property-inclusion: non_null`（`application.yml:8`）会让 `null` 字段**从 JSON 里整个消失**：`page`、`failReason`、`stage`、`vectorRate`、`sampleLimit` 等都可能不在响应里，前端必须按"字段可能不存在"来写。
2. `score` 是 0-1 的余弦相似度（`PgChunkStore` 里 `1 - 距离`），SSE 侧保留 3 位小数；它与其余 0-100 的百分比字段刻度不同。
3. 时间戳一律 BIGINT 毫秒，时区由 `hibernate.jdbc.time_zone: Asia/Shanghai` 决定。
4. `documents.progress` 是真实批次计数，不是定时器；`stage`（解析阶段）第八批起落 `documents.stage` **可空列**，**发版前入库的历史行读为 NULL**，前端按状态兜底显示"处理中"（不是丢数据）。
5. 实体用的是 **public 字段**而非 getter/setter（如 `CitationEntity.java:13-33`），Hibernate 走字段访问。加缓存或写 DTO 映射时注意这点。

## 5. 核心功能详设

每个模块按同一结构：页面布局 → 业务逻辑 → 接口 → 字段与校验 → 状态机 → 权限 → 异常与边界 → 能力边界。

### 5.1 登录与身份认证

**页面布局**（`LoginView.vue`）：左侧品牌展示区（产品名 + Slogan + 能力要点），右侧表单：账号、密码、"记住登录"勾选、登录按钮。
`[未实现]` 没有"忘记密码"入口、没有 SSO 统一登录（前后端都没有对应实现）。

**业务逻辑**

1. 前端本地校验（见字段表），不通过则按钮置灰。
2. `POST /api/auth/login`，请求体字段名是 **`account`**（不是 `email`），值为邮箱或工号。
3. 成功：`{token, refreshToken, expiresAt, user{id,name,account,role,dept}}` → 写 localStorage 四个 key（`zd_token` / `zd_refresh_token` / `zd_user` / 勾选记住时 `zd_remember_account`）→ Pinia 更新 → 跳 `/chat`。
4. 失败：401 统一文案，不区分账号不存在与口令错误。
5. 冷却：同一账号连续失败 5 次 → 429 + `retryAfter:60`，前端按 `retryAfter` 倒计时禁用。
6. 刷新页面：`store.restore()` 用 localStorage 令牌调 `GET /api/auth/me` 恢复；401 时 axios 拦截器**单飞**刷新 access token 并重放一次原请求，刷新也失败则清态跳登录。

**字段与校验**

| 字段 | 必填 | 规则 | 默认 | 不满足 |
|---|---|---|---|---|
| 企业账号 | 是 | 邮箱或工号，≤50 字符，非空 | 记住上次（若勾选） | 按钮置灰 + 表单提示 |
| 密码 | 是 | 6-32 位 | 无 | 同上 |
| 记住登录 | 否 | Boolean | 勾选 | — |

**异常**：网络异常时表单顶部给出可刷新提示；后端 5xx 显示"服务暂不可用"。

**权限**：公开端点。登录后角色决定导航项。

**能力边界**：access token 8h、refresh token 7d（`JwtService.java:14,19`）；有刷新接口但**无撤销、无轮换**；SSO、忘记密码、图形验证码均无实现（D-25）。

### 5.2 智能问答（核心模块）

**页面布局**（`ChatView.vue`）：左栏会话列表（新建 + 历史，按 `updated_at` 倒序）；右栏自上而下：会话头部（标题 + 知识库连接状态）→ 多智能体管道条带（深色）→ 消息流 → 输入区 → 引用溯源提示。**原先消息流与输入区之间有一排"示例问题"快捷标签（四条写死的提问 + 一行说明文字），2026-10-02 按用户指令整体去除**——那四条是随演示语料写死的，语料删空后点它们只会得到拒答，属于把人往错的地方引；空会话时页面只剩 `.chat-page__empty` 的提示与输入框。

**业务逻辑（完整实现口径）**

| 阶段 | 实现 | 关键点 |
|---|---|---|
| 发起 | 前端拼 `{conversationId, question, knowledgeBaseIds}` 调 `POST /api/chat/stream`。**问题 1-500 字由后端校验**，越界直接 400「问题需为 1-500 字」（`ChatService.java:88-91`） | `[已修 D-11，第七批]` 请求体**不再带 `history`**（老版本它后端从未读取）。多轮上下文改为**只从服务端会话记录取**（`Conversation.messages`，重启后由 `messages` 表回填，顺序由 `@OrderBy("ord ASC")` 保证）——客户端传的历史一律不采信，否则任何人都能往模型里塞指令 |
| 意图 | `intent` 节点：正则判断问题类型，产出 `detail` 文本 | **不调模型**。`[边界]` 它是正则规则，不是智能体 |
| 检索规划 | `queryRewrite=true` 时先生成 `multiQueryCount` 个扩展查询（连同原问题一起 embed）→ 每个向量各跑一次 pgvector 近邻 → 按分块取最高分去重 → `scoreThreshold` 过滤 → `topK` 截断 | 参数来自 `settings_rag`，热生效。可见库集合见 §3.4。**问答走严格路径** `retrieveForChat`：embed 必须来自真实服务，失败整体重试 `CHAT_ATTEMPTS=3` 次（退避 `500*attempt` ms，每次重试通过 `onRetry` 回调发一条 `agent-update{retrieval,running,"检索失败，正在第 N 次重试…"}`），仍失败抛 `RetrievalFailedException` → `error{retryable:true}` 且**不进入生成阶段**（`RetrievalService.java:51-92`、`ChatService.java:220-231`）。其中"配置层就没有真向量"（`HashVectorRejectedException`）会**跳出重试循环**直接失败——重试三次和重试一次结果一样，不该白烧退避时间。**评测自第六批起走这同一条路径**（D-28 已修；曾经的容错入口 `retrieve()` 已删除，见 §5.5.2） |
| 知识合成 | 取前 `MAX_CITATIONS=4` 个分块进 prompt（每块截 `SNIPPET_CHARS=700` 字），LLM 流式生成；生成后**规整行内标号**：剔除越界编号、去重相邻重复 | `SynthesisPrompt.java:21-22`。资料行只在 `page>0` 时写"第 N 页"（`:46`），无页边界就只写文档名——**不向模型谎报页码**，否则它会照抄进答案。**system 提示词第 4 条（2026-10-02 加）要求输出纯文本**：不得出现 `#` 标题、`*`/`-` 列表、`**加粗**`、反引号、`>` 引用、`|` 表格，分点用"1. 2. 3."写成普通段落行。理由是**前端本来就不做 Markdown 渲染**（`MessageBubble` 走纯文本 + 保留换行，全仓无 `v-html`/`marked`），模型给的 `**…**` 会**原样显示成星号**，用户读到的是噪音而不是强调。这条只约束文风，不影响 `[n]` 标号规整与引用卡片生成 |
| 多轮上下文 | `messages` 数组 = `system` + **本会话最近 `app.chat.context-turns` 轮**（1 轮 = 一问一答两条消息，默认 3 即 6 条）+ 本轮 `user`（`OpenAiCompatibleLlmProvider.java:95-105`）。历史每条同样截 700 字 | `[已修 D-11]` 三条刻意的取舍：① 历史里的行内 `[n]` **先剔掉再进模型**——那些编号指向上一轮的资料，留着等于让模型把旧编号抄进新答案、引用卡片指向错文档；② system 里明写"之前的对话只用于理解指代，不是事实来源"，本轮结论仍须落在【资料】上；③ **只有真实模型吃上下文**，`MockLlmProvider` 是模板拼装、看了历史也不会有不同输出，所以降级时前端不会显示"本轮带 N 条会话上下文"（显示了就是谎报）。`[边界]` **检索仍只用当前问题原文**（加关键词式查询改写），"上面那条的第二点"这种指代要靠模型理解，检索阶段不做共指消解 |
| 引用下发 | 检索完成即以**单个** `citation` 数组事件一次性下发（不是逐条） | 卡片含 `id/doc/docId/page/chunkIndex/snippet/score`；`page<=0` 时置 `null`（`SynthesisPrompt.java:96`），字段随 `non_null` 序列化直接消失。**PDF 现在带真实页号**（D-4 已修，逐页抽取），无页边界概念的类型仍走"字段缺席"。前端 `citeWhere()` 的口径因此是"**有页码显示第 N 页，没有就显示分块号**"，不是猜一个页码。`[边界]` 重生成（D-1）**不会重发引用**：数组只在第 1 轮下发，重写轮共用同一批 `hits`，卡片与编号自始至终同一套 |
| 质量验证 | LLM-as-Judge 做一次忠实度打分；`qualityPassed = 引用非空 && (judge 成功 ? score>=60 : 回答含 "[1]")` | `[已修 D-1，第七批]` 未通过会**触发有界重生成闭环**：`app.chat.quality-retries`（默认 1，实现里钳制在 **0-2**）规定额外重写次数，每轮 = 一次合成 + 一次判定，所以默认最坏是 2 轮模型调用。`[边界]` **只重生成、不重检索**——`hits` 全程复用同一批片段；能修的是"没标号/夹带资料外说法/组织混乱"，资料里本来就没有答案的问题重试多少次都还是不过。因此第 2 轮必须带改进指令（`SynthesisPrompt.retryDirective(reason)` 拼在本轮 **user prompt 末尾**，不进 system），否则同 prompt 同温度重采样等于白烧一次调用。两条硬边界：**mock 降级路径不重试**（模板拼装不看判定结果，重试只会原地复制同一份文案）；**未通过校验的答案不回填缓存**（否则一个低质答案会在 TTL 窗口内被反复回放） |
| 零命中 | 先 `warning{type:"no-result"}`；`synthesis` 标 running/detail="检索零命中，不调用模型作答（防幻觉拒答）"；**下发 1 个 `token` 事件承载固定拒答文案**（四行：说明 + 三条建议，`ChatService.java:333-338`）；`synthesis→done`、`validation→failed`；`done` 带 `qualityPassed:false`、`noHit:true`；**不给 citation 事件**，但拒答正文照样落 `messages` | 这是刻意的拒答，不是失败。注意它仍是**一个 token 帧**，所以 AC-1 的 `tokenFrames>1` 判据在零命中场景必然不成立 |
| 缓存 | 命中 `chat:<sha1(代号+问题+范围+历史窗口)>` 则直接回放：`intent/retrieval/synthesis` 三段标 **`skipped`**（detail 写"命中回答缓存（Redis TTL 600s）…"），`validation` 沿用缓存结论给 `done`/`failed`，答案作为**单个 `token` 帧**下发，`done` 带 `cached:true` | `skipped` 只在缓存回放路径出现，实时路径不会有。`[已修 D-11]` 第四段 key 是**本轮进 prompt 的那段消息 id 窗口**（`ChatService.historyKey()`）：没有历史时是空串，所以"各会话的首轮同一个问题"仍能互相命中（结论与上下文无关）；一旦带了历史，同题不同上下文必然落到不同 key——否则追问会直接拿首轮答案回放。用 id 不用内容做指纹：消息落库后内容不改，id 相同即上下文相同 |
| 缓存失效 | 代号 `chat:gen` 一变，所有旧 key 立刻读不到（不 SCAN、不 DEL，旧 key 靠自身 TTL 消失）。触发点：**摄取写块成功、摄取失败清块、删文档、删知识库、改知识库 `scope`/`members`** | `[已修 D-33]` 回填用**查缓存时拿到的同一个代号**，所以"生成途中有人改库"的迟到写入落在旧代号上、自然不可读。Redis 不可时代号走内存且重启归零 |
| 护栏 | 提问先过 `ChatGuard`（在取缓存**之前**）：日成本熔断 → 单用户当日次数 → 在途并发，任一不过就整条拒绝，不占 worker、不读写缓存；通过后占用一个在途名额，流终止（正常/异常/取消）由 `doFinally` 归还 | 参数与口径见 §3.8、§8.1。被拒时下发 `error{code, retryAfter, retryable:true}`，**HTTP 状态仍是 200**——`text/event-stream` 的状态行此时已提交 |
| 中断 | 客户端断开即终止；同一用户新请求会向旧流推 `error{message:"已被新的提问打断", retryable:false}` 后取消（按 user.id 互斥） | `ChatService.java:183-189` |
| 落库 | 会话 + user/assistant 两条分块 + 引用行；`title` 见 §4.4.4 | 引用行含 `chunk_index`（列见 §4.4.6），回看与实时字段一致；`doc_id` 不做级联清理，文档删后卡片点不开（§4.4.6） |

**SSE 协议（实现版，8 类事件）**

| event | data（实测字段） | 前端行为 |
|---|---|---|
| `start` | `{conversationId, messageId}` | 建 AI 气泡 |
| `agent-update` | `{step:"intent\|retrieval\|synthesis\|validation", status, detail?}`，`status ∈ running\|done\|failed\|skipped` | 点亮管道节点。`[边界]` 前端类型里有第 5 个状态 `pending`（`types/api.ts:55`、`ChatView.vue:160-163`），**后端从未下发它**，它只是本地"未开始"初始态 |
| `token` | `{text}` | 流式追加 + 光标闪烁 |
| `citation` | `[{id,doc,docId,page,chunkIndex,snippet,score}]`（一次性数组） | 生成引用卡片 |
| `revision` | `{attempt,reason}` | `[已修 D-1]` **上一版作废**：质量校验没过、后端要带改进指令重写，前端必须清空已显示正文（`ChatView.vue` 的 `onRevision` 置 `content=''` 并记 `revisedFrom`），否则两版会拼在同一条消息里。`reason` 是判定给出的原因，前端只作为徽标的悬停提示，不进气泡正文。只在真实重生成时出现，最多 `quality-retries` 帧 |
| `warning` | `{type:"no-result"}` | 零命中告警标识 |
| `error` | `{message, retryable}`；被护栏拒绝时另有 `code`（`TOO_MANY_INFLIGHT`/`DAILY_QUOTA`/`COST_BREAKER`）与 `retryAfter`（秒） | 错误 + 重试按钮。前端目前只用 `message`/`retryable`，多余字段忽略不报错 |
| `done` | **三条路径字段不同，前端必须按可选字段处理**：<br>· 实时生成：`{conversationId,messageId,qualityPassed,attempts,model,provider,vectors,llmAvailable}`<br>· 缓存回放：`{conversationId,messageId,qualityPassed,cached}`<br>· 零命中拒答：`{conversationId,messageId,qualityPassed,noHit}` | 收尾。`model/provider/vectors/llmAvailable` 用于如实显示"这次是谁答的、用的哪种向量后端"，**缓存与拒答路径没有这四个字段**。`attempts`（第七批 D-1）= 本轮**实际发生的生成次数**，`1` 即一次过、没有 `revision`；**缓存回放路径故意不带**（那一次没有做过任何生成，写 `0` 或 `1` 都是谎报），前端类型因此是可选的 |

**没有独立的接口契约文档**（旧的契约文件已删除），`done` 的真实字段以 §5.2.3 的三条路径为准；验收脚本正在读 `model/vectors/llmAvailable/cached/noHit`。字段只散落在 controller 与本文档里，改后端字段没有任何机制提醒同步文档（`[缺陷 D-13]`）。

**输入校验**：问题 1-500 字，前端超长即截断提醒；`Enter` 发送 / `Shift+Enter` 换行；输入长度为 0 时发送按钮禁用。

**异常与边界**

| 情形 | 表现 |
|---|---|
| 在途/日次数/日成本超限 | `error{code, retryAfter, retryable:true}`，本次不检索、不调模型、不落会话。三档默认 2/24、200 次、800 元，次日零点恢复（成本熔断同） |
| SSE 连接断开 | 气泡尾部出现"重试"按钮（`retryable:true`） |
| LLM 服务超时 | `error{retryable:true}`。后端 LLM 超时 `LLM_TIMEOUT=120s`（可配） |
| LLM 不可用（mock） | 回答仍产出，`done.provider=mock`、`/api/health status=DEGRADED`。**不会假装是真模型答案** |
| embedding 无密钥 | `[已修 D-14，第五批]` **默认拒绝**：严格路径抛 `HashVectorRejectedException`，问答出 `error{retryable:true}` 且不进入生成、入库停在 `FAILED`——不再写 1024 维哈希假向量。只有显式 `LLM_ALLOW_HASH_VECTORS=true` 才回退到 mock 嵌入，且每次写入伴随一条 WARN |
| pgvector 降级 | 检索走内存实现，`done.vectors=memory`，监控中心出"向量检索已降级"告警 |
| nginx 缓冲打开 | token 会在末尾一次性到达、首 Token 指标失真。配置里已 `proxy_buffering off`，改动后必须实测 |

**能力边界汇总**：无 LangChain4j 编排、无真正的多智能体、无断点续传（断线只能整条重试）；多轮上下文只进生成、**不进检索**（D-11 已修的范围内）；质量重试**只重写不重检**，且次数有界（`quality-retries` 上限 2）、降级路径不重试（D-1 已修的范围内）。

### 5.3 知识库管理

**页面布局**（`KnowledgeView.vue`）：顶部四张统计卡（总分块数 / 库数量 / 向量化成功率 / 每日缓存 Tokens），下方知识库卡片网格（库名、分块规模、可见范围、覆盖率进度条、连接状态）。
`[缺陷 D-15 已修，第六批]` 该页原先**只有"新建"没有编辑/删除入口**（后端 `PUT/DELETE /api/knowledge-bases/{id}` 存在但 UI 调不到）。现在卡片底部有"编辑/删除"，与新建共用同一个对话框（`editingId` 决定走 `PUT` 还是 `POST`）；两个界面内前置的后端硬规则：**已存在的库不许改成机密**（"机密"选项置灰 + 说明，不是隐藏），**库里还有文档时删库会被拒**（先提示文档数，让人去文档管理删）。"批量导入变更"入口仍在（D-6 那批加的 `canWrite` 门控下）。

**业务逻辑**

- 进页面调 `GET /api/knowledge-bases/overview`，返回 `{totalChunks, kbCount, vectorRate, totalDocs, dailyLlmTokens, vectorStore, embeddingModel, bases[]}`。
- `vectorRate = 已完成向量化的文档数 / 文档总数`；**没有文档时返回 `null`** → 前端"—"，不是 0%。
- `dailyLlmTokens` 取 Redis 当日计数（含 embedding 调用），取不到为 `null`。
- `embeddingModel` 取自全局设置——**全系统只有一个 embedding 模型，不随库变化**。`[未实现]` 没有"每库单独选 Embedding 模型"，换模型 = 全库重嵌入。
- `status` 由真实状态推导：向量库非 pgvector → `disconnected`；有未完成解析任务 → `syncing`；否则 `connected`。
- 列表按可见性过滤（§3.4）并**按 `created_at` 升序**（不是按名字）。第八批起这句落在 SQL 上：可见性判定每请求直读 `knowledge_bases`（含 `kb_members` 批取，`@BatchSize(50)`），**共享/取消共享立即生效**——原先知识库镜像只在启动装载一次，改完共享不重启根本看不见变化（D-30 的"正确性单点"就是这条）。users 仍按 60s 重载，账号被禁用或删除最迟 60s 后在鉴权侧生效。

**字段与校验**

| 字段 | 必填 | 规则 | 默认 |
|---|---|---|---|
| 名称 | 是 | 2-30 字；**且不得与其它库同名**（trim + 忽略大小写后相等即同名，第九批 D-2 起在写入侧拒绝，**不是数据库约束**） | 无 |
| 可见范围 | 是 | `public`/`internal`/`dept`/`confidential` | `internal` |
| 成员 | 否 | `dept` 及以上生效；只接受四种形态（user id / 工号 / 账号 / `dept:部门名`），**逐项硬校验**（D-7）：非 `dept:` 形态必须对上真实用户，否则 400 指名哪一项写错；`dept:` 允许暂时没人（只 WARN）。上限 200 项、单项 ≤80 字 | 空 |
| Embedding 模型 | — | **接口不接受**（`KbRequest(name, scope, members)`，`KnowledgeBaseController.java:46`） | 全局值 |

**状态机**：无（库本身没有状态字段，`status` 是每次请求现算的）。

**权限**：读 JWT；写 `KM_ADMIN+`；机密库创建需 `?confirm=true`（428）。

**异常**：pgvector 不可达时卡片显示"断开"并给错误摘要；**库里仍有文档时删库直接 400**（"知识库下仍有文档，请先删除文档"，`KnowledgeBaseController.java:155-156`）——空库才会被删，同时清掉该库遗留的向量与 PG 侧 `chunks`（`chunkStore.deleteByKb`），**不是**级联删文档。**建库/改名撞上同名 → 400 `KB_NAME_DUPLICATE`**（第九批 D-2，口径见 §4.7；判重排在 428 机密二次确认之后，所以机密库的确认流程不受它影响）。改可见范围或成员会推 `chat:gen` 代号让回答缓存整体失效（§4.6、D-33）；**仅改名不推**——判定条件是 `scopeOrMembersChanged`，缓存键与库名无关（`KnowledgeBaseController.java:144`）。

### 5.4 文档管理与入库

**页面布局**（`DocumentsView.vue`）：顶部工具栏（搜索框、状态分段筛选 全部/处理中/已入库/失败、批量操作、上传按钮）；下方表格列 = 文档、类型、所属知识库、分块数、状态、更新时间、操作；解析中行内进度条；点击行展开分块预览。

**业务逻辑**

1. 上传：`POST /api/documents/upload` multipart（`file` + `kbId`）→ 立即返回文档对象（`status=PARSING`），后台 2 线程池异步处理。**两个部件都是 multipart part**：`kbId` 绑的是 `@RequestPart`，不是 query 参数——WebFlux 不会把 `@RequestParam` 回退到表单字段，这一点在第八批被我改错、导致线上上传整体不可用（**D-39，已改回、待发版**）。检查顺序是刻意的：**扩展名白名单（无 I/O，在 Netty 线程上）→ 验库存在 + `canSee` → 同库同名判重 → 建目录并落盘 → 体积校验**（`DocumentController.upload`）。"先验库再落盘"是为了无权写对方的库时连文件都不该碰，"**同名判重必须排在 `transferTo` 之前**"（第九批 D-2）是为了被拒的那次不在 `uploads` 卷里留一份没人认领的文件——撞上就 400 `DOC_NAME_DUPLICATE`，要替换只能先删旧文档（删除会一并清向量与落盘文件）。`[未实现]` 没有分片直传、没有对象存储、没有回调通知（§2.4）。
2. 类型白名单 `pdf/docx/xlsx/txt/md`（`DocumentController.java:33`），否则 400 `UNSUPPORTED_TYPE`。
3. 大小校验：`FilePart` 给不了可信的 Content-Length，所以是**落盘后**用 `Files.size` 判 `app.upload.max-size-mb`（默认 50），空文件与超限都返回 400 并删掉刚落盘的那份；线上超 nginx `client_max_body_size 50m` 时仍是 413 且后端日志看不到请求。两道闸的口径不同，本机裸跑只有前一道。
4. 解析（D-4 第四批改过）：抽取按类型分流——**PDF 用 PDFBox 逐页抽文本**（`IngestService.extractPdfPages`，页边界真实；加密/纯扫描件等逐页拿不到文本时退回 Tika 整篇，页码如实留"未知"），txt/md 直读 + 去 BOM，其余走 Tika 整篇 → `TextChunker`（500 字符 / 100 重叠，**按字符不是按 token**）**每页各自分块、块不跨页**（跨页块没有唯一页码，引用卡片就无从定位）→ 分批 embedding（批大小 10）→ 写 `chunks`。**副作用**：同一篇 PDF 重新入库后分块数通常比原先多（块不再跨页），空白页不产块。
5. `progress` 是真实批次计数：0 → 25（抽取完）→ 50（分块完）→ `50 + 25*doneBatches/totalBatches` → 100。失败重置 0 并记 `failReason`（截 200 字）。
6. 前端每 2500ms 轮询列表；批量删除是**串行**逐个 `DELETE`。
7. 删除三步：MySQL 行 → 向量 → 磁盘文件，**非事务**；磁盘删除失败只打 WARN（库里和向量里已经干净，会留下孤儿文件）。`[缺陷 D-17]`
8. 启动时 `reconcileInterruptedIngest` 把上次进程遗留的 `PARSING` 收敛为 `FAILED`（否则会永远显示"解析中"）；同一处另有 `reconcileInterruptedEvalRuns` 把遗留的评测 `running` 收敛为 `failed` 并另存 `interruptedProgress`（D-18）。

**状态机**

| 当前 | 可执行 | 下一状态 | 触发 |
|---|---|---|---|
| `PENDING` | （实际不可达） | — | 上传即 `PARSING` |
| `PARSING` | 等待 | `READY` | 全部块向量化并写库成功 |
| `PARSING` | — | `FAILED` | 解析或入库异常 |
| `FAILED` | 重试 / 删除 | `PARSING` | 新解析任务 |
| `READY` | 重试（后门） | `PARSING` | 见下 |

**retry 准入**（`DocumentController.java:177-186`）：`FAILED` 可重试；另外"`READY` 且 `chunkCount>0` 但向量库里实际 0 块"也允许——这是给降级期丢向量留的自愈后门。其他 `READY` 文档重试会被拒。**D-4 的连带影响**：已入库的旧 PDF 不会因为这次发版自动获得页码，而它们又是 `READY` 且向量齐全，走不到 retry——要让它们带页码，只能删除后重传（不要为此放宽准入判断，也不要手工删 `chunks` 行，见 §4.5 的对账约定）。

**接口**

| 接口 | 说明 |
|---|---|
| `GET /api/documents?keyword=&status=&kbId=&page=1&size=20` | `{total, items[]}`，`size` 钳制在 **1..100**（`DocumentController.java:72-73`，D-10）。**`kbId` 是 2026-10-02 补上的可选库过滤（D-40）**：给了就只返回该库的文档，**库不存在 → 400、库存在但你看不见 → 403**，绝不静默返回空清单——因为"以为过滤生效了"正是那次误删的使能条件（`缺陷与技术债.md` §5.11）。第八批后它不再是"读内存镜像"：可见性判定 + 全表文档读 + Java 侧过滤分页，**每请求一次 MySQL**（前端文档页每 2500ms 轮询的就是它，见 §2.4）。第九批 D-2 给它补了 `idx_documents_updated_at`（排序落在索引上），但**改成 SQL 侧过滤与分页仍没做**——`total` 的语义被 `run.mjs` 与语料导出脚本依赖，见 `缺陷与技术债.md` §5.8 边界 ⑧ |
| `GET /api/documents/{id}` | 详情，**额外返回 `vectorStore`**（运维探针，前端不消费它，但验收前置在读） |
| `GET /api/documents/{id}/chunks?page=` | 分页，**每页固定 10 条**（`DocumentController.java:161`），返回 `[{index,text,charCount,page}]`；`page` 只在真实页号时出现，无页边界的块**没有这个字段**（`:170`） |
| `POST /api/documents/{id}/retry` | 见状态机 |
| `DELETE /api/documents/{id}` | 三步删除 |

**权限**：读 JWT（含 `EMPLOYEE`，见 D-6）；写 `KM_ADMIN+`。

**异常**：分块预览与声明块数不一致 → 说明写库中断，用 retry 后门补齐。块没有页码时前端**不显示"第 N 页"**（分块预览用真值判断 `v-if="c.page"`，引用卡片退化成"分块 #N"）——这是正确行为，不是缺数据；反过来，**页码永远不编造**。损坏/加密/无文本层的 PDF 走"退回 Tika 整篇"，抽取仍然空 → `FAILED`，AC-3 的"坏 PDF → FAILED → retry 200"判据不受影响。**同名文档被拒时的界面表现要提前知道**：element-plus 上传组件的 `on-error` 把**整个响应体**当错误文案显示，用户看到的是 `上传失败：{"code":"DOC_NAME_DUPLICATE","message":"…"}` 这样一整段 JSON——既有的体积超限（D-16）就是这个形态，第九批没有改前端，不要把它当成新引入的 bug。

#### 5.5.1 题库（`golden_questions`）

#### 5.5.2 评测运行

**页面布局**：上方标题 + "题集选择/运行评测"；主体左栏五项质量指标（进度条 + 数值 + 目标线），右栏历史趋势柱状图；下方报告区是两栏网格（`.eval-report__body`）——左为**运行列表**（点一行选一次运行），右为**逐样本打分明细**与导出；窄屏（`<1200`）竖排成单列。
`[宽度口径]` 运行列表六列宽合计 **550px**，网格左轨在 `@media (min-width:1200px)` 里写成 `minmax(560px, 5fr)` 兜住这个下限，所以它**不出横向滚动条**（这张表也不带 `scrollbar-always-on`——那是 2026-10-02 从它身上摘掉的，理由见 `缺陷与技术债.md` 的 D-20 追记）；右轨写 `minmax(0, 7fr)` 允许被压小，因为逐样本明细表列宽合计约 900、本来就一直常驻滚动（D-20 的取舍）。**这些数字全部是算出来的**：内容区宽＝视口−240（侧栏）−32（页 padding）−32（卡片 padding），本机没有可用视口，未在浏览器里实测过一帧。

**业务逻辑**

1. `POST /api/eval/run`，body `{questionIds?}`。**空 body = 取全部"已复核且启用"的题**；显式勾选里含未复核题 → 400 `INVALID_PARAM`；没有任何可用题 → 400 `GOLDEN_EMPTY`，文案原文包含"没有已复核的考卷时跑出来的分数没有测量含义，不如不出分"（`EvalService.java:98-100`）。已有任务在跑 → 409 `EVAL_RUNNING`。**评测是单实例串行**，不排队。
2. 返回 `{runId, status:"running"}`，异步执行；前端轮 `GET /api/eval/runs` 看 `metrics.progress`。第八批（D-30）之后**趋势 `/api/eval/trend` 与监控的幻觉率读数**改走 `RunHead` 投影（`select` 指定列、**不取 `samples_json`**）；**`/api/eval/runs` 列表本身仍按行读 `samples_json`**，因为 `EvalRun.view(false)` 无条件带 `scores` 数组、列表要逐题画分（`EvalView.vue:149`）。原先"启动灌一次整表、之后从内存切片"变成"每次轮询直读 MySQL"，代价随历史运行数线性增长——这是 D-30 的**残留**，消除它要改前端（列表不画分、点开再取），见 `缺陷与技术债.md` §5.8 边界 ⑫。
3. **每题的取数路径与线上问答同源（D-28 已修，第六批）**：
   - 检索走 `RetrievalService.retrieveForChat(viewer, question, null, attempt->{})`——**就是问答那一条严格路径**。容错入口 `retrieve()`、`Embedder` 抽象与 `EmbeddingService` 的降级方法已整体删除，评测不再可能"在假向量上跑出好看的分数"。失败语义分两种：**配置层就没有真向量**（`HashVectorRejectedException`，如没配 `LLM_API_KEY` 又没开 `LLM_ALLOW_HASH_VECTORS`）→ **整轮直接 `failed`、不出分**（重试多少次都一样，白烧 token）；**瞬时失败**（网络/超时）→ 该样本记 `retrievalFailed:true`、无答案、不进模型判定，但**仍留在检索准确率的分母里**拖低分数。宁可分数难看，也不靠剔除失败样本美化。
   - 发起人身份是**当前登录用户**（`EvalController.run` 取 `CurrentUser.of(ex)` 传下去），检索按**他可见的知识库**过滤。以前固定用"第一个 SYS_ADMIN"（`pickEvaluator()`，已删），那意味着 KM_ADMIN 点一下评测就能把机密库的内容算进全站分数——评测口径与问答口径不是同一个可见性，现在才是同一个。期望文档在机密库里的题，需要由 SYS_ADMIN 发起才会被检到（前端题集选择框上写了这句）。
   - 合成走 `EvalService.synthesize()`，非流式，也不写会话表。
   - **每轮落一条检索环境快照** `env`：发起人/角色、`vectorStore`（pgvector 或 memory）、`embedMode`、chat 模型、RAG 三参（topK/阈值/是否查询改写）、judge 并发、请求样本数、`degraded`。存 `eval_runs.env_json`（TEXT，可空），失败原因存 `fail_reason`（500 字，超长截断）。列表页"发起人 / 环境"列显示"发起人 · 向量库 · 向量化"三段（`envBrief`），`degraded` 标红；**没有这份快照就没人能事后判断两次运行能不能比**。
4. 打分：
   - **检索准确率**（规则）：`hit` 样本占比。`hit` 的判据是**文档名双向 `contains` 匹配** `expected_doc`（`EvalService.java:163-164`）——不是标题精确相等，改名后仍能命中。另有两条边界登记为 **D-49**：`expectedDoc` 为空串时 `contains` **恒为真**（现在跑不出这种题，唯一兜底是复核门禁 `GoldenQuestionService.java:118`），而文档名太短会命中原不该命中的文档（写 `报告` 就能命中所有名字含"报告"的）——两者的后果都是**检索准确率无声上浮**，不报错也不留痕迹。
   - **引用完整率**（规则）：`min(100, 去重标号数 * 100 / 系统给出的引用卡片数)`；卡片数受 `MAX_CITATIONS=4` 限制，分母为 0 或标号为 0 时得 0 分（`EvalService.java:296-298`）。**分母是"系统给出的卡片数"，不是"答案里引用了几篇文献"** —— 它度量的是"给出的卡片是否都被标出来"，检索是否命中期望文档由检索准确率负责。
   - **相关度 / 忠实度 / 幻觉率**（LLM-as-Judge，`qwen-plus`，并发 `LLM_JUDGE_CONCURRENCY=4`）：**只汇总判定成功的样本**，分母是 `judgedByLlm`；`judged=0` 时三项写 `-1.0` 表示"未判定"，前端显示"未判定"且不画柱。
   - Judge 失败或输出不可解析 → 该样本 `judge:"rule-fallback"`，**不进这三项的分母**，相关度用规则值（命中 85 / 未命中 40）；但**仍计入检索准确率与引用完整率的分母**（它们是规则指标，与模型判定无关）。
   - `metrics.retrievalFailedCount` = 本轮检索失败的样本数，前端在它还大于 0 时挂一条警示："失败题仍计入分母，分数要重新跑一次才算数"。样本级 `judge` 对这类题写 `"retrieval-failed"`（既不是模型判定也不是 rule-fallback）。
5. 样本级 `passed = 检索命中 && 标号数>0 && 非 ruleFallback && 相关度>=85 && 忠实度>=88 && 幻觉率<=5`（`EvalService.java:235-236`）。
6. 完成后 `metrics_json` + `samples_json` 落 `eval_runs`，同时写入 `question_ids` 快照与 `question_signature`。
7. `EVAL_SAMPLE_LIMIT`（`app.eval.sample-limit`）>0 时截取前 N 条控成本；默认 0 = 全量，此时响应里的 `sampleLimit` 为 `null`（字段直接消失）。

**指标目标**（配置常量，非测量值）：检索准确率≥90、相关度≥85、忠实度≥88、幻觉率≤5、引用完整率≥90（0-100 刻度）。

**可比性规则**：趋势图里**只有 `questionSignature` 相同的运行才是一条测量线**，换题集就是另起一条。前端必须显示指纹与题数。**第二条轴是 `env`**：题集相同但 `vectorStore`/`embedMode`/RAG 参数不同，仍然是两次不同的测量，`degraded=true` 的那一轮在列表里显式标红；早于本次改动的旧运行**没有 env**，界面写"旧运行（无环境快照）"。`[边界]` env 只是**摆出来给人看**的，代码不会因为 env 不同而拒绝把两次运行画进同一条趋势线——判"能不能比"仍然是读图人的责任。旧记录若来自已删除的语料，其分数不代表当前系统（见 §11.4）。

**异常**：`GOLDEN_EMPTY`(400) / `INVALID_PARAM`(400) / `EVAL_RUNNING`(409) / `EXPORT_FAILED`(500)。评测中途进程重启留下的 `status=running` 僵尸行，启动时由 `SeedInitializer.reconcileInterruptedEvalRuns` 收敛为 `failed` 并把冻住的进度另存 `interruptedProgress`（D-18 已修）。注意 `EVAL_RUNNING` 只在**同一进程内**成立：`evalRunning` 是内存标志，重启即复位，僵尸行不会挡住新评测。

### 5.6 监控中心

**页面布局**（`MonitorView.vue`）：上方运行指标卡（P50 / P95 / 采样数），两栏为请求量趋势与 LLM 成本看板，底部告警列表。每 30000ms 自刷新。
`[边界]` 没有"服务可用性 %"、没有"Pod 健康数"这类字段（曾经有，已删）——单进程应用无从测量，任何这类数字都是编的。

**业务逻辑**

- 采集：`MetricsWebFilter` 对**任何以 `/api` 开头的请求**记录耗时与按分钟分桶（`MetricsWebFilter.java:24-30`、`Store.java:51,56-60`）。
- 环形缓冲 `RING_MAX=2000`：**只保留本进程最近 2000 条**，重启清零，跨进程不汇总。`latencySamples=0` 时两个分位数没有意义。
- P50/P95：排序后 `idx = ceil(0.95*size)-1`。**空数组时返回 `null`**，配合 `non_null` 序列化就是整个字段缺席（不是 0），前端与脚本"读不到 = 没测到"（D-19 已修）。
- 请求量趋势 `requestTrend`：近 30 个自然分钟的真实计数，按 epoch 分钟分桶，**没有流量就是 0，不补曲线**。
- 成本：`cost.today` 是按 `LLM_PRICE_PER_1K`（默认 0.0008 ¥/1K tokens）**估算**的金额，`amountIsEstimate:true`、`thresholdSource` 标出阈值来自配置项 `MONITOR_COST_THRESHOLD`（默认 600 ¥/日）。**不是账单**。同一只数字现在还被 `ChatGuard` 当熔断依据消费（`CHAT_COST_BREAKER_YUAN`，默认 800）——**单价配错，熔断线一起错**。
- 告警有四条真实规则（`MonitorService.alerts`）：

| 规则 | 阈值 | 无数据时 |
|---|---|---|
| P95 延迟 | > 2000ms（硬编码，不可配） | 采样 0 条 → 文案"P95 未测得（未测得不等于达标）"，不触发 |
| 幻觉率 | > 10%，取最近一次 `done` 评测 | **"尚无已完成的评测，幻觉率未知（未评测不等于合格）"** |
| 向量检索降级 | 当前为内存实现即报 | — |
| 当日估算费用 | ≥ `MONITOR_COST_THRESHOLD`（告警线，低于 `CHAT_COST_BREAKER_YUAN` 熔断线） | Redis 不可用时读进程内兜底计数，只有本进程 |

**用户管理字段与校验**（`SettingsController.java:143-235`，全部是应用层校验，数据库无约束）

| 字段 | 必填 | 规则 | 违反 |
|---|---|---|---|
| `account` | 是 | `trim` 后非空、≤50，且匹配邮箱 `^[\w.+-]+@[\w-]+(\.[\w-]+)+$` **或** 工号 `^[A-Za-z0-9_-]{4,50}$` | 400「账号需为邮箱或工号（4-50 位）」 |
| `name` | 是 | 非空 | 400「姓名不能为空」 |
| `password` | 创建必填 | 6-32 位；编辑时可省略（省略=不改） | 400「密码需为 6-32 位」 |
| `role` | 是 | 枚举 `EMPLOYEE`/`KM_ADMIN`/`SYS_ADMIN` | 400「role 非法」 |
| `empNo` | 否 | 空白转 `null`、`trim` 存储；**且不得与任何人的账号或工号撞车**（见下） | — |
| `dept` | 否 | **缺省填「综合管理部」** | — |

**唯一性只在应用层查**（`SettingsController.requireDistinctIdentity`，第九批 D-2 统一）：新值与**其它每一个用户**的 `account`、`emp_no` 做忽略大小写的交叉比对，撞上就 400，文案点名"这个登录标识已经是「某某（账号）」的登录标识"。四条口径值得单独记：

- **交叉方向都查**：`account` 撞别人的 `emp_no` 也算撞车。以前只比同名列，这一方向能通过——`userByAccount` 是"先按账号查、再按工号查"，撞车的结果是那个工号永远解析到账号持有者，**另一个人无声地登不进来**（登录 500 或直接失败，看不出是被谁挡的）。
- **为什么"账号与工号都能登录"就必须整体不撞**：两个登录入口指向同一字符串时，系统只能有一个主人。
- **更新路径只在值真的变化时校验**，且 `selfId` 排除自己——否则存量里已经存在的撞车会让那个用户的姓名、部门都改不动。**清空工号按"空串→`null`"处理**：一堆 `""` 会让"按工号登录"命中多行、`userByAccount` 抛 `NonUniqueResultException`，登录直接 500。
- **`emp_no` 没有任何数据库唯一约束**（`users.account` 的列级 unique 是全项目唯一一条，历史遗留），这段循环比对是唯一防线；它读后写、不原子，也**不会自动发现存量的撞车**（只拦"以后"，核对 SQL 见 `DEPLOY.md` §10.1）。

**四条自我保护 / 失管保护**（都不作用于"改别人的资料"）：

| 场景 | 结果 |
|---|---|
| 修改自己的角色为**非** SYS_ADMIN | 400「不能修改自己的角色。需要移交管理员权限，请用另一个系统管理员账号操作本页面」 |
| 停用当前登录账号 | 400「不能停用当前登录账号」 |
| 降级/停用某 SYS_ADMIN 后**启用中的管理员将 ≤0**（`activeAdminCount()<=1`） | 400「系统里只剩这一名启用中的系统管理员，不能再降级或停用」 |
| 删除自己 | 400「不能删除当前登录账号」 |
| 删除内置超管账号 | 400「内置超管账号不可删除」（判据是 `SettingsController` 里的账号名常量） |

> 也就是说：**单个管理员可以把自己以外的一切改掉，但不会把自己关在门外**。移交管理员必须有两个 SYS_ADMIN 账号。没有"重置密码后强制改密"、没有首次登录改密（`[未实现]`）。

**注意**：`baseUrl` 改动会立刻影响下一次真实调用；把 LLM 设为 `mock` 需要在环境变量层改（`LLM_PROVIDER=mock`），UI 不提供。

## 6. 接口契约汇总

### 6.1 统一响应与错误码

- Base URL `/api`；鉴权 `Authorization: Bearer <JWT>`；错误体 `{code, message[, retryAfter]}`。
- 成功响应无包装信封（直接返回业务对象/数组）；`null` 字段被 Jackson 省略。
- 百分比字段一律 **0-100 数值**，后端产出的就是百分数，前端不得再乘 100（唯一例外是引用 `score`，0-1）。

| HTTP | code | 触发 |
|---|---|---|
| 400 | `INVALID_PARAM` | 字段校验失败（名称长度、评测勾选未复核题、设置项越界等），**以及题库判重、账号/工号撞车**（第九批 D-2，两者都走 `BizException.badRequest`，文案点名冲突对象） |
| 400 | `UNSUPPORTED_TYPE` | 上传扩展名不在白名单 |
| 400 | `DOC_NAME_DUPLICATE` | 同一知识库内已有同名文档（第九批 D-2，代码层判重，非数据库约束；§4.7、§5.4） |
| 400 | `KB_NAME_DUPLICATE` | 知识库重名（同上；建库与改名两处，改自己成原名不挡自己） |
| 400 | `GOLDEN_EMPTY` | 没有"已复核且启用"的题目却要求出分 |
| 401 | `UNAUTHORIZED` | 三档文案见 §3.2 |
| 401 | `BAD_CREDENTIALS` | 账号或密码不正确 |
| 401 | `INVALID_REFRESH_TOKEN` | 刷新令牌无效/过期 |
| 403 | `FORBIDDEN` | 角色矩阵，文案见 §3.2 |
| 404 | `NOT_FOUND` | 文档/库/会话/题目不存在；**以及根本没映射上的路径**（"拼错 URL"原先被 `ApiExceptionHandler` 的 `Exception` 兜底判成 500、并把框架内部文案 `No static resource api/xxx.` 透给客户端；`ResourceWebHandler` 抛的是 `ResponseStatusException(404)`，2026-10-02 单独分出这一支，其余状态维持原样。代码已改，**要下次发版才在线上生效**） |
| 409 | `EVAL_RUNNING` | 已有评测在跑 |
| 428 | `CONFIRM_REQUIRED` | 机密库未带 `confirm=true` |
| 429 | `TOO_MANY_REQUESTS` | 登录冷却，带 `retryAfter`。**这是全站唯一的 429 状态码** |
| SSE `error` 事件 | `TOO_MANY_INFLIGHT` / `DAILY_QUOTA` / `COST_BREAKER` | 问答护栏拒绝（§5.2、§3.8）。HTTP 仍是 200：`text/event-stream` 的状态行在判定完成前已提交，所以拒绝只能走事件载荷，`retryAfter` 一并带在 data 里 |
| 500 | `UPLOAD_FAILED` | 上传文件落盘失败（`DocumentController.java:112-113`） |
| 500 | `STORAGE_ERROR` / `EXPORT_FAILED` / `INTERNAL_ERROR` | 磁盘/导出/兜底 |

### 6.3 前后端边界（不变式）

- 所有流式生成由**单一 SSE 端点**承担，前端不直连 LLM。
- 引用溯源数据由**后端检索阶段**生成并随回答下发，前端只渲染、不做检索、不猜页码。
- 多智能体管道状态**仅作可视化**，不承载业务正确性判断（真正的判定是 `qualityPassed`）。
- 任何"未知"必须由后端返回 `null`/`-1` 表达，前端不得自行补 0 或 100%。

### 8.2 compose 强制非空的 7 个密钥（`${VAR:?}`）

`MYSQL_USER`、`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`PG_USER`、`PG_PASSWORD`、`JWT_SECRET`、`LLM_API_KEY`。

任一未定义或为空 → `docker compose` **直接报错退出**，不会带着空值起来。这是刻意拦截：`LLM_API_KEY` 缺失时问答退 mock、向量化则被 D-14 的闸门**直接拒绝**（§2.5、§5.2），两种都不是一台"能跑但结论不可信"的机器该有的样子。

护栏与限额类变量（`CHAT_*`、`STORE_USER_CACHE_TTL`、`UPLOAD_MAX_MB`、`LLM_ALLOW_HASH_VECTORS`）在 compose 里是 `${VAR:-默认值}` **透传**：不填就用 yml 默认值。之所以要在 compose 显式列一行，是因为没声明的变量根本不会进容器，"只在 `.env` 里写了"等于没改。

### 8.3 热生效 vs 需重启

| 改动 | 生效 |
|---|---|
| 设置页的 chat/embedding 配置、RAG 四参数 | **热生效**（下次调用即读 `settings_*`） |
| `.env` 里任何一项 | 需 `docker compose up -d` 重建后端容器 |
| `LLM_EMBED_DIM` / 换 embedding 模型 | 需重启，**且会清空 `chunks`**，必须重新上传/重嵌入全部语料 |
| `nginx.conf` | 需重建前端镜像（`COPY` 进镜像，非挂载） |
| Java 代码 / Vue 代码 | 需重新走发版（§9） |

## 10. 可观测性与运维

### 10.1 `/api/health`（公开，容器 healthcheck 用）

```json
{"status":"UP|DEGRADED","llm":"openai-compatible|mock","vectorStore":"pgvector|memory",
 "pendingVectorOps":0,"redis":"redis|in-memory","users":…,"documents":…}
```

（`users`/`documents` 是读数，形状如上、数值随环境而变，别把任何具体数字当基线。）

- **进程能应答就返回 200**，降级不作为存活失败依据（否则 pgvector 抖动会让 compose 反复重启）。
- 探针**只读内存状态，不访问数据库**——真去连库会把观测变成降级副作用的触发点（MySQL 抖一下就把"进程能应答即 200"变成容器重启）。第八批删掉业务表镜像后这条**刻意保持**：`users` 仍取鉴权镜像，`documents` 改取一个同周期（`STORE_USER_CACHE_TTL`）刷新的 **COUNT 仪表值**，不是实时精确计数、最多滞后一个周期，MySQL 读失败时保留上一次的旧值。启动装载完成前两者都可能为 0；**MySQL 载入失败时 `documents` 显示 0**，看不出"是空的"还是"没连上"，要用启动日志那行 `业务数据:` 区分（§10.2 第 8 步）。
- `start_period: 180s`：启动要探测 LLM/pgvector，留足余量。
- 上线必查这五个字段，不要只看 `docker compose ps` 的 Up：

  ```bash
  # [服务器] 8080 只绑 127.0.0.1，外部访问不到，必须在服务器上执行
  curl -s http://127.0.0.1:8080/api/health
  ```

  | 字段 | 上线期望值 | 不是这个值说明什么 |
  |---|---|---|
  | `status` | `UP` | `DEGRADED` = LLM 或向量库至少一个已降级，仍可访问 |
  | `llm` | `openai-compatible` | `mock` = 没给 `LLM_API_KEY`、`LLM_PROVIDER=mock`，或启动探活失败。两种情形都**不会再写假向量**（D-14 已修），但表现不同：**压根没有真实服务**（前两种）→ 向量化被 `HashVectorRejectedException` 直接拒，文档停在 `FAILED`、问答检索立刻报错，不做无谓重试；**有真实服务但这次没通**（探活失败/key 无效）→ 仍会真打接口，按 `CHAT_ATTEMPTS=3` 退避重试后抛 `RetrievalFailedException`。哈希假向量（与真向量同维、事后无法区分）只有在 `LLM_ALLOW_HASH_VECTORS=true` 时才写得进去，那是本机调试专用 |
  | `vectorStore` | `pgvector` | `memory` = 内存里没有语料，全站答"未检索到" |
  | `pendingVectorOps` | `0` | >0 = 降级窗口的写在排队（上限 2000，超出丢弃），恢复回放后应归零 |
  | `redis` | `redis` | `in-memory` = 回答缓存与成本统计只在本进程，重启即丢 |

### 10.2 日志与启动动作清单

`SeedInitializer.run()`（`seed/SeedInitializer.java`，符号名为准、行号随改动漂移）的真实顺序。**任一步失败都不阻断启动**，只在日志里留痕：

1. `db.loadAll()` 只灌两样东西：**`users` 鉴权镜像**与运行期配置（模型/RAG 参数），并把 `documents` 的仪表值取一次快照。**不再整表灌业务数据**（D-30 第八批）。失败 → `log.error(...)` 并把 `mysqlLoaded` 置为 false。
2. `users` 表为空时 `seedAdminAccount()` 创建**一个内置超管账号**（账号名是代码常量，本文不复述；口令来自 `ADMIN_INIT_PASSWORD`，留空则随机生成并**只在启动日志打印一次**，日志翻过去就找不回来了）。
3. **`mysqlLoaded=false` 时第 4~6 步整体跳过**并打一条 WARN——这三步都会写数据或删数据，拿读不到的清单去跑比不跑危险得多。
4. `reconcileInterruptedIngest()` 用一条 `where status in ('PARSING','PENDING')` 把上次进程遗留的解析中文档收敛为 `FAILED`（并把 `stage` 一并写 `failed`），让用户能点重试。
5. `reconcileInterruptedEvalRuns()` 把停在 `running` 的评测行收敛为 `failed`，冻住的进度另存 `interruptedProgress`（D-18）。
6. `reconcileOrphanVectors()` 清孤儿向量：基准是 `SELECT id FROM documents`，**这条读失败就整体跳过**（半截基准等于删光整库向量）。日志形如 `向量库对账: 文档 xxx（名称（n 块））已不存在，清掉其遗留的 n 个向量分块`。
7. `migratePlaintextPasswords()` 明文口令 → BCrypt。
8. 未被第 2 步播种过时打印一行 `业务数据: users=… kbs=… docs=… chunks=…`——**上线后第一时间看这行**，它比 `/api/health` 更早暴露"MySQL 没连上/向量库空了"。这里面的 `kbs`/`docs` 是启动时各一次真实 `COUNT`，与探活那个滞后仪表值是两回事。

外部服务的健康探测与降级判断**不在 `SeedInitializer`**：分别由 `llm/LlmConfig`（`probe-on-startup` 探 LLM，探不通回落 mock）、`rag/PgConfig` + `monitor/StartupHealth`（探 pgvector，失败进内存实现）完成。所以"启动日志里没有 health-check 字样"不代表没探测。

日志读取（两种环境分开讲）：
- `[容器]` UTF-8，直接 `docker compose logs -f backend`。
- `[本机]` 中文 Windows 上裸跑 jar 落盘是 **GBK**，`grep` 会当二进制跳过。完整读法：`iconv -f GBK -t UTF-8 backend.log | grep -a "业务数据"`。`-a` 必须加——`iconv` 遇到不可映射字节仍可能输出二进制片段，不加 grep 就整行不匹配。

## 11. 验收标准与测试工具链

### 11.1 AC-1 ~ AC-6 的实现侧判定口径

验收套件：`scripts/acceptance/run.mjs`（npm 封装：`accept` / `accept:eval` / `accept:bootstrap` / `accept:keep`）。退出码 0=全通过、1=有未达项、2=执行异常。结果只打印 stdout，**不落文件不落库**。**口令一律从环境变量来**（`ACCEPT_ADMIN_PW` / `ACCEPT_KM_PW` / `ACCEPT_EMP_PW`，账号名可用 `ACCEPT_ADMIN` 等覆盖），缺失即退出，脚本里不再落任何凭据字面值。

> **全项目没有任何单元测试。** `backend/src/test` 目录不存在（`pom.xml` 引入了 `spring-boot-starter-test`，但没有一个 `*Test.java`），前端没有 vitest 配置与测试文件。下面这六条 AC 是本项目**唯一的自动化验证**，而它是端到端的：要连三套数据服务、要打真实 LLM 与 embedding、要花钱。所以"改了代码没跑 accept 就说没坏"这个说法在本项目不成立——没有任何东西能替代它。

#### AC-1 问答全链路

- 验收目标（脚本自述）：提问 → 多智能体 → 流式输出 → 引用完整可用。
- 脚本判定（`run.mjs:222-279`）：`start` 帧带 `conversationId` 与 `messageId`；`intent`/`retrieval`/`synthesis`/`validation` 四段都出现过 `running` 与 `done`；`tokenFrames > 1`；引用卡片 `cites.length > 0`；`done.qualityPassed === true`。
- **重生成判据（第七批 D-1 加的，`run.mjs:243-250`）**：读 `done.attempts` 与 `revision` 帧数，判"revision 帧数 == attempts-1"。**它是自洽性检查，不是有效性检查**：一次过（`attempts` 缺省或 `1`）时判据**如实 SKIP**，因为判定没过才会触发重写，谁也造不出这一帧。要真验出重生成，得先让 Judge 判出低分——而 AC-1 的主问恰好设计成能过的。所以"accept 全绿"绝不等于"重试管线跑过"。
- **多轮上下文两条判据（第七批 D-11 加的）**：① 在同一会话里追一个问，`synthesis` 的 `detail` 必须出现"本轮带 N 条会话上下文"——读的是后端自己拼的展示文案，不去猜模型说了什么；`done.provider` 不是 `openai-compatible` 时**如实 SKIP**（本地模板不吃上下文，标了就是谎报），追问本身零命中时也没有 `provider`，同样 SKIP。② 把**完全相同的第一问**在同一会话里再问一遍，`done.cached` 必须不是 `true` 且 `noHit` 不为 `true`——首轮那次已经回填过缓存，若历史没进 key，这一句就会被回放成首轮答案。**这条现在被首轮结果门控（D-1 的连带改动）**：只有首轮 `qualityPassed===true` 才会有缓存可回放，首轮没过就判 SKIP，否则"没东西可回放"会被白捡成 PASS。判据 ② 在 `CHAT_CACHE_ENABLED=false` 时恒过（没东西可回放），属已知盲区，别把它当缓存功能的证明。**代价：AC-1 至少 3 次真实模型调用（主问 + 追问 + 重问），而每一次都可能在判定后多烧一轮重生成，最坏是 6 次。**
- 实现真相：`qualityPassed` 的 60 分阈值**在后端**不在脚本（`ChatService.java:299-300`），且它是"有引用卡片 **且**（Judge 判过时 `score>=60` **或** Judge 未判时答案含 `[1]`）"的复合式——不是纯质量分。另有一条**只在后端成立的副作用**：过了这条判定才回填缓存（`ChatService.java:315`），所以脚本里"第二次问同一题没被回放"这件事，在首轮没过判定时是白给的，不能作为缓存生效的证据（上面判据 ② 的门控就是为此）。
- 判定风险：`kbIds:['kb-policy']` 已在第三批改为 `kbIds=null`（＝当前角色全部可见库），所以 AC-1 现在**要求库里真的有可检索分块**，空库由 preflight 显式 SKIP 中止（§11.4 第 2、3 条已按此更新）。`tokenFrames>1` 只在实时管线成立，命中缓存时后端只发 **1 个** token 帧（`ChatService.java:166`），会被判 FAIL——这不是缺陷，是缓存路径本就不做打字机效果。

#### AC-2 引用溯源

- 验收目标（脚本自述）：每个 `[n]` 都能定位到来源文档；**分页格式（PDF）还必须定位到页码**。
- 脚本判定（`run.mjs:282-321`）：行内标号集合非空；每个标号有卡片、卡片有 `doc`、`GET /documents/{docId}` 返回 200；然后**按文档类型分判据**（`:288` 的 `PAGINATED = new Set(['pdf'])`）——`type=pdf` 必须有 `typeof c.page === 'number' && c.page > 0`，非分页格式若 `page` 缺席则必须有 `chunkIndex`，两者都没有才算"定位不到片段"（`:299-300`）；零命中场景必须 `warning>0 && citation==0` 且答案含"未检索到"、不含 `[n]`。通过时的证据串带类型与定位信息：`[n]文档名(pdf) p.3 chunk#7 score 0.62`。
- 实现真相：零命中刻意用**新建空库**来测——默认阈值 0.15 下，生僻问题在全库检索仍会弱命中，直接问站外问题测不出拒答分支。
- **原先"这一条必 FAIL"的根因已修（D-4，第四批）**：PDF 改逐页抽取后 `page` 是真实页号，卡片不再必然字段缺席。判据同步改过——旧写法无条件要求 `typeof c.page === 'number'`，等于**逼 docx/txt 编造页码**，那是判据本身不正确而不是实现没问题。**这条现在能 PASS 的前提仍然是"库里有已重新入库的 PDF"**：修复前入库的旧 PDF 依旧 `page=0`（字段缺席），AC-2 会对它报"pdf 的引用没有页码"，这是如实结果，不是脚本抖动（§5.4 retry 准入那段说明了怎么让它带页码）。

#### AC-3 文档解析

- 验收目标（脚本自述）：解析成功率 ≥95%，失败可重试。
- 脚本判定（`run.mjs:324-422`）：名字写 ≥95%，**实际要求 6 种格式 6/6 到 READY**（样本只有 6 个，95% 阈值在这里等价于"一个都不许失败"）；正文关键句真的进了分块（防"状态成功但内容为空的空壳成功"）；坏 PDF → `FAILED` → `retry` 200；翻页拉全库分块预览，与声明块数一致。
- 实现真相：尾页判据是"每页 10 条、返回 `<10` 即尾页"，与 `DocumentController.java:161` 的 `int size = 10` 硬耦合——后端改分页大小，这条会静默算错而不是报错。D-4 的"每页各自分块"不改变这条成立（`chunkCount` 与实际写库块数仍由同一趟流水线得出），但**同一篇 PDF 重新入库后块数会变多**，跨轮次比较块数没有意义。

#### AC-4 权限隔离

- 验收目标（脚本自述）：员工仅能检索公开库，越权接口 403。
- 脚本判定（`run.mjs:425-497`）：员工库列表只含 public；**引用级差分**（取员工回答的每条引用卡片，用 **admin** 身份把 `docId` 解析成 `kbId`，该 `kbId` 必须在员工可见集合内）；**员工答案不得出现"仅管理员引用到"的文档名**、且 **admin 可见库集合 ⊇ emp 可见库集合**（第三批改造：原先这两条判的是演示语料里的 `4.82 / 2.95`，语料删除后就是无意义断言）；员工上传 403（库 id 给占位串即可，403 来自角色矩阵、先于库校验）；监控/审计/用户管理 403；未登录与伪造令牌 401；机密库先 428 再 `confirm=true` 200；错误口令统一 401（不区分"账号不存在"与"口令错"）。
- 实现真相：引用级校验比"接口 403"更有价值，它直接测 §3.4 的 `Visibility.canSee` 而不是测 URL 矩阵。**注意它测不到 D-6**：AC-4 校验的是"问答引用是否越界"，脚本没有"以员工身份直接 `GET /documents/{别人库的 docId}` 应当 403"这一项——而且真加了会失败，因为该接口对 `EMPLOYEE` 放行；解析 `kbId` 这一步本身就是借 admin 权限做的。

#### AC-5 响应性能

- 验收目标（脚本自述）：首 Token <1s、P95 <2s、SSE 支持中断重连。
- 脚本判定（`run.mjs:500-558`）：5 个问题串行，`firstTokenMs` 取**中位数 <1000**；`tokenSpreadMs>1000` 用来证明真的是增量下发而非一次性整段；`monitor.p95Ms<2000`，**`p95Ms` 字段缺席则判 SKIP（未测得不等于达标，第三批改的，同 D-19/D-22 口径）**；`abort` 后能重新发起；会话 HTTP 200。证据串打的是真实字段（`latencySamples`、`cost.today`），不再引用早已不存在的 `availability/healthyPods/totalPods`。
- 实现真相与口径：
  - 首 Token 从 `fetch` 前打点到**首个 token 帧解析完成**，含连接建立 + 鉴权 + 检索 + 首块生成，不是后端自报的服务端时间。这与"模型首 Token 延迟"的字面口径不同，实测值天然偏大。
  - n=5 时脚本算的"中位数"是第 3 个样本，它写的"P95"实际就是**最大值**——5 个点谈不上分位数。
  - `monitor.p95Ms` 来自进程内环形缓冲，且**包含了噪声流量**：容器 healthcheck 每 15s `curl /api/health`（≈每分钟 4 次）、前端监控页每 30s 自轮询（`MonitorView.vue:99`）、文档页解析中每 2.5s 轮询（`DocumentsView.vue:179`）都会进同一只桶（`MetricsWebFilter.java:25` 只按 `/api` 前缀过滤，没有排除健康探针）。这些探针延迟极低，会把 P95 **往下压**。
  - 空缓冲的假 PASS 已消除：`percentile([])` 返回 `null`（D-19 已修），字段随 `non_null` 整个缺席，`m?.p95Ms != null && <2000` 不再成立。脚本侧对 `-1`（未判定）的误判仍待修（D-22）。

#### AC-6 评测达标

- 验收目标（脚本自述）：检索 ≥90 / 相关度 ≥85 / 忠实度 ≥88 / 幻觉 ≤5 / 引用完整率 ≥90。
- 脚本判定（`run.mjs` 的 `ac6()`，行号随改动漂移）：默认 **SKIP**，只有 `--eval` 才跑；POST `/eval/run` 拿 `runId` 后按 `for (i<240) sleep(5000)` 轮询，即**最长 20 分钟**（这是代码里的上限，不是估算值），`status` 为 `done` **或 `failed`** 都立即跳出（第六批起 failed 会是"整轮没出分"，继续轮询只是白等）；对 `LIMITS` 五项逐条比阈值，**但先问"测得出来吗"**：值为 `-1`（后端"未判定"哨兵）或字段缺席一律判 SKIP、从分母剔除，不再出现 `hallucinationRate=-1 ≤ 5 → PASS` 这种假通过（第三批修 D-22）；`samples.length > 0`；JSONL 导出行数 >1。**本轮新增的两条判据（随 D-28）**：① `env` 里必须同时有 `vectorStore` 与 `embedMode`，否则判 FAIL 并打印发起人/角色/RAG 参数/`degraded`——没有环境快照的这一轮无法与任何历史运行对比；② `metrics.retrievalFailedCount` 存在时单列一条判据，>0 判 FAIL 并说明"失败题仍计入分母，分数要重新跑才算数"；运行 `status=failed` 则直接输出 `failReason` 并结束，不再拿空指标去比阈值。
- 实现真相：分母与 `-1` 哨兵规则见 §5.5.2。`-1 <= 5` 在 JS 里成立，所以**全未判定时 `hallucinationRate` 曾被判成 PASS** —— 这是 D-22 的原始形态，第三批在 `:605` 用 `typeof v === 'number' && v >= 0` 先过一道再比阈值，五项判定都不会把"没测到"读成"达标"。另外脚本用 `role:'km'` 触发评测：**第六批之后发起人身份就是可见范围**（`pickEvaluator()` 已删，评测按发起人的可见库检索，D-28 已修），所以 KM_ADMIN 跑出来的分数不再包含机密库内容——期望文档若放在机密库里，这一题会算作未命中，需要 SYS_ADMIN 发起才可比。这是口径变化，不是回归。

### 11.3 测试数据处置约定

共享库（与线上同一实例）**允许测试写入但必须事后清理**；清理靠 `created` 登记表逐条 `DELETE`，删除失败被 `.catch(()=>{})` 静默吞掉，所以跑完要**复查一次**列表而不是相信脚本的"已清理"。`eval_runs` 与 `audit_logs` **不由脚本清理**（后端没有删除接口），必须手工 SQL。

### 11.4 当前 AC 能不能判？—— 不能，且原因要写清

这一节是本文档最重要的结论之一：**历史 AC 数值全部作废，且现在跑不出任何数值。**

1. **历史数值已作废**。`README.md` 的"当前实测状态（2026-09-26）"记的 AC-6 引用完整率 70.3 / 幻觉率 6.7、AC-5 首 Token 3.8-7.2s，是在 21 篇演示语料 + 旧口径下测的；2026-09-29 做了两件事：① 演示语料与四个库全部删除（线上现在 `documents=0, chunks=0`）；② 指标口径变更（引用完整率改为"去重标号数 / **系统给出的引用卡片数**"封顶 100，公式的权威表述在 §5.5.2；三项主观指标只汇总 Judge 成功样本、全未判定返回 `-1`）。两组数字都**不代表当前系统**，不得继续引用。
2. **空库会明确中止，不再崩溃**。前置 `preflight()` 读 `GET /documents?page=1&size=1`，文档或分块为空时先记一条 `ENV / 库里有可检索的分块 → SKIP`，再 `throw new Error('文档/分块为空，中止')`（`run.mjs:168-171`）。六条 AC 还是一条都不执行，但输出是"环境前置不满足"而不是空数组上的 TypeError。**这只是让"跑不了"变得诚实，并没有让 AC 能跑。**
3. **AC-1/AC-2/AC-4 已不再依赖已删的演示语料**（第三批 D-12）。原先写死的 `kbIds:['kb-policy']`（该库随演示数据一起删除，`scopeOf` 会静默丢弃不存在的库 → 必 FAIL）改为 `{ kbIds: null }` = 全库检索；AC-4 的两条断言换成与正文内容无关的不变量 —— "员工答案里不得出现*只有管理员才引用到*的文档名" 与 "管理员可见库集合 ⊇ 员工可见库集合"；越权上传改传占位 id（403 来自角色矩阵，与该库是否存在无关）。**但脚本仍然需要语料**：零分块时引用链无从产生，前置照样中止。那批演示正文的唯一副本仍是仓库根 `corpus-backup.jsonl`（21 行 / 121 块 / 4 个库）。
4. **AC-6 拒绝出分**。没有任何"已复核且启用"的题目时后端返回 400 `GOLDEN_EMPTY`（当前题库为空），脚本判 FAIL——这是前置缺失，不是质量结论。
5. **"未判定"现在一律 SKIP，不再假 PASS**（第三批 D-22，配合第一批 D-19）。AC-5 用 `m?.p95Ms == null ? null : m.p95Ms < 2000`（字段缺席即 SKIP）；AC-6 对每个 judge 维度先判 `typeof v === 'number' && v >= 0`，`-1`（后端哨兵）与字段缺席都记 SKIP 并注明"judge 未运行或无样本，不计入达标"。汇总表按 `通过/(总数-SKIP)` 出数，所以 **SKIP 是从分母里剔除的** —— 引用结论时必须连带看 SKIP 条数，否则"6/6 通过"可能是"6 条里 5 条没测到"。
6. **AC-2 那条独立的必失败项已解除**（第四批 D-4）。原先"卡片必然没有 `page`"是因为抽取不记录页边界；现在 PDF 走 PDFBox 逐页抽取，卡片带真实页号，判据也改为按类型要求"页码或分块序号"（§11.1 AC-2）。**注意解除的是"必 FAIL"，不是"必 PASS"**：判 PASS 仍要有可检索语料，且语料里得有**修复后重新入库的 PDF**——修复前入库的旧 PDF 仍是 `page=0`、字段缺席，会被如实判为"pdf 的引用没有页码"。
7. **唯一与历史语料无关的是 AC-3**（夹具全内存生成），但仍被前置拦住；且它的"全库分块预览一致"一项在 0 文档下是"无测量对象"的空转通过，不具备验收效力。

顺带一处**曾误导排障的脚本注释已改写**（第三批）：`run.mjs` 前置段原先两处写着"降级是粘性的、只有重启才会恢复（见 `DelegatingChunkStore.degrade`）"，与 §2.5 的实况相反 —— `PgStoreRecovery` 每 `PG_REPROBE_MS`(默认 30s) 重探，探通自动切回并回放排队写。现在注释与报错文案都按"等它切回 pgvector 或查 PG 健康后再跑"来写，并按此在**收尾复查**降级（跑测途中 pg 瞬断会把 AC-2/AC-3 变成内存结果，复查把它标成环境问题而非产品缺陷）。

**要重新得到 AC 结论，前置条件是**：① 上传真实语料（脚本已不再依赖演示库名和演示数字，但零分块时前置照样中止）；② 录入并复核 ≥1 题；③ 从 `.env` 提供 `ACCEPT_ADMIN_PW`/`ACCEPT_KM_PW`/`ACCEPT_EMP_PW`（缺失时 `loginAll()` 启动即抛，不再回落到源码里的口令字面值）；④ 语料里至少一篇 **PDF 且是在这次发版之后入库的**（D-4 已在第四批修掉，但旧 PDF 不会自动补页码，见 §5.4）——否则 AC-2 仍会因"pdf 引用没有页码"判 FAIL；⑤ 发版带上对账逻辑（§10.2 第 6 步）后确认 `chunks` 与文档数一致。

### 12.1 常被当成"已有"、其实代码里没有的东西

这一节的判据只有一条：**在 `backend/src` 与 `frontend/src` 里找不到实现**。左列是容易被误当成既有能力的说法（来自同类 RAG 产品的常见配置，或本仓库早期文档里的设想），右列是当前代码的实况。

|---|---|---|
| Spring AI + **LangChain4j** 多智能体编排 | 单一 `ChatService` 顺序管线，`pom.xml` 里**没有 LangChain4j 依赖** | "多智能体"只是四段管线的可视化。要真正的编排是重写，不是改配置 |

| 性能优化 / 索引 / 水平扩展 | **热点读的 12 条索引已在实体上声明**（第九批 D-2，§4.7：按仓库里真实存在的查询形态来定，含三处有意不加）。仍没有的：文档列表与题库的 **SQL 侧过滤分页**（现在还是全表读 + Java 侧筛）、会话读取的 **JPA EAGER 逐条展开**（一条 40 消息的会话几十条 SQL）、`KnowledgeBaseController.view` 的 **N+1**（每个可见库各做一次 PG 计数 + MySQL 全量物化文档，只为数个数）、水平扩展 | 当前是单实例形态；索引让**每一次**读变便宜，但没减少**次数**，这三条读放大仍在（§13 D-30/D-2 边界） |

> - **目标地址无缺省值**：`ZD_BASE` 没注入就打印一行提示并 `exit 2`。脚本里已不再有任何生产地址字面值 —— 原来 `ACCEPT_BASE` 缺省指向线上（"忘了设变量就把生产删空"）是 D-27 的核心风险，现已消除。
> - **口令无缺省值**：`ZD_PASS` 没注入同样 `exit 2`。`ZD_ADMIN` 仍缺省为内置超管账号名，那是 `SeedInitializer` 写死的常量、不是凭据，换账号时才需要注入。口令轮换后注入旧值仍会 401，但 401 是登录失败，不会走到删除。
> - **删除动作有前置确认**：先要求 `corpus-backup.jsonl` 存在且 >1000 字节 → 登录并打印"当前指向哪个 BASE" → 分页拉全文档/库并**逐条打印待删清单** → `--dry-run` 到此返回；默认还要求**手输 `delete-all`**，输错即退出且不删任何东西；只有显式 `--yes` 免交互（给自动化用，慎用）。
>
> 闸门再多也不能替代一次核对。跑之前做这两步（`export` 只读，任何时候可以先跑；删除按"先 `export` 拿到备份并核对行数 → 再 `delete`"的顺序）：
>
> ```bash
> # [执行脚本的那台机器] 把 BASE 当成"我要删的是哪套"来验证，别凭记忆
> export ZD_BASE=http://127.0.0.1:8080/api     # 本机裸跑的后端——试 delete 只可以用这个
> # 生产地址本文不复述，也不写在脚本里（这正是 D-27 改的点）；真要删生产时由操作者显式注入
> curl -s "$ZD_BASE/health"
> ```
>
> BASE **必须带 `/api` 后缀**，脚本内部直接拼 `$BASE/documents` 这类路径；漏掉 `/api` 会一路 404，看起来像"服务没数据"。
> 把返回的 `users` / `documents` 与你**打算删的那套环境**的实际数字对上：对不上就是打错了目标（最常见的情况是本机没起服务、请求实际落到了线上）。删完用同一个 BASE 再 curl 一次，期望 `documents=0` ——**但 `documents` 现在是按 `STORE_USER_CACHE_TTL`（默认 60s）刷新的仪表读数，删完立刻查可能还是旧值**，等一个周期再核对，别把它当成"删除没生效"（更权威的核对是 `/api/documents` 列表本身，它每请求直读 MySQL）。同时确认 `chunks`（`/api/knowledge-bases/overview` 的 `totalChunks`）也归零——向量清理走的是删除链路，MySQL 删了而向量没删会留下孤儿（要等下次启动对账才收，见 §10.2 第 6 步）。
